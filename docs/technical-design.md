## 1. 链选型与 Gas 支付问题（核心决策）

### 1.1 Discord / Telegram 用户能否自己付 gas？——结论：原生场景下「很难」

把区块链当后端、把聊天软件当客户端，会撞上一个结构性矛盾：

1. **聊天用户默认没有钱包**。Discord / Telegram 账号 ≠ 区块链地址。要让用户「自己付 gas」，前提是他得先有一个持有 CFX（或任何原生币）的钱包——这直接劝退 99% 的聊天用户。
2. **钱包审批会打断聊天流**。即使接入钱包，「在群里发一句指令 → 弹出钱包签名 → 等待上链」的体验，与「在群里聊天即游戏」的初衷相悖。
3. **原生 CFX 获取门槛**。即便有钱包，还要先买 CFX，对纯聊天玩家是额外负担。

所以：**在「纯聊天客户端」前提下，指望用户用自己的钱包原生支付 gas，UX 不成立。** 这不是 Conflux 特有的问题，所有 EVM 链都一样。

### 1.2 「代付 gas」的几种方案对比

| 方案 | 机制 | 用户是否付 gas | 是否需要 Core Space | 评价 |
|------|------|----------------|---------------------|------|
| A. 用户原生自付 | 用户钱包直接发交易 | 是（CFX） | 否 | UX 差，需钱包，不适合聊天场景 |
| B. Conflux Core Space 代付 | Core Space 原生 sponsor 机制，白名单内调用由赞助者付 gas | 否（赞助者付） | **是** | 用户仍需 Core Space 钱包并签名；且 Core Space 非纯 EVM（地址/账户模型不同） |
| C. 中继器 + 元交易（Relayer / Meta-Tx） | 玩家用聊天身份授权，Bot 用自己的钱包代为发交易并付 gas | 否（中继者付 CFX） | 否 | **用户零钱包摩擦**；中继成本按通道分级回收（L1a 免费配额封顶补贴 / L1b 充值付费，§1.5），不依赖游戏币回补 |
| D. 托管账户（Custodial） | Bot 掌握玩家账户私钥，代玩家发交易 | 否（运营付） | 否 | 最顺滑，但中心化托管，需明确信任模型 |

### 1.3 是否需要 Conflux Core Space 代付？——**结论：不必要，不建议**

- 你的硬性偏好是「纯 EVM」。**Conflux Core Space 并不是 EVM 等价**（它使用自己的账户/地址格式与存储模型），而 **Conflux eSpace 是完整 EVM 兼容**。选型应优先 eSpace，以契合「纯 EVM 链」目标。
- Core Space 的代付本质是「赞助者付 gas + 用户仍需 Core 钱包签名」。相比而言，**方案 C（中继器 + 元交易）在 eSpace 上能做到用户连钱包都不需要**，体验更好，且不锁定到 Core Space。
- 因此：**我不认为 Core Space 代付 gas 是「非常必要」的**。用 **eSpace + 中继器** 即可覆盖代付需求，且更灵活（回补逻辑写在你自己的合约里）。

### 1.4 推荐架构：eSpace + 中继器 + 游戏币回收（解决「不想一直补贴」）

为了同时满足「聊天体验顺滑」和「不想永久补贴 gas」，采用 **方案 C 的演进版**：

```
玩家(Discord/TG) ──聊天指令──> Bot(中继器/信任锚)
                                      │ 用 Bot 自己的钱包发交易
                                      ▼
                              Conflux eSpace 合约  ←── 预言机/Keeper 也走这里
```

- **玩家不持钥匙**：聊天身份（Discord user id / TG user id）映射到链上 `playerId`，授权由「聊天身份」担保，Bot 是信任锚与代签者。
- **Bot 付 CFX gas，且不是永久白贴——按通道分级回收**（详见 §1.5 三层通道表与 §6.4）：
  - **L1a 免费档**：每账号每日小额免费动作配额，是获客支出，**总量被配额硬性封顶**；
  - **L1b 充值档**：玩家向官方充值 CFX/美元，按动作计费（gas × (1+服务费率)）——**gas 成本回收的主力通道**；
  - 游戏内对每类动作收取的**游戏币动作费**只是链上层的**防刷摩擦与速率限制**（进 GasTreasury 销毁），**不构成 CFX 回补闭环**；
  - 效果：**重度聊天用户要么付费（L1b）、要么迁移 CLI 自付（L2），免费补贴只覆盖轻度新用户**——保住聊天 UX 的同时避免无限补贴。

### 1.5 方案 E：自托管 CLI 客户端（用户真正「自主支付 gas」的路径）

补充一条重要方案：官方提供**开源命令行程序（CLI，Command-Line Interface，命令行界面）**，玩家在自己的电脑上运行：

- **私钥本地持有**：玩家在 CLI 中导入自己的 eSpace 私钥（本地加密保存或环境变量引用），私钥**永不离开本机**。
- **直连链上、自付 gas**：CLI 通过公共 RPC（Remote Procedure Call，远程过程调用）节点直接发送交易——排技能、加入房间、逃离、开菜契等全部动作由玩家自己的钱包签名并支付 gas。**没有任何中继，没有托管**。
- **回写聊天频道**：CLI 同时作为一个轻量聊天机器人，把玩家自己的动作（「我安排了下回合用斩铁剑」）**发送到指定的 Discord 频道或 Telegram 群**——群友无论用哪种客户端，看到的信息流是一致的。
- **队长主播模式**：队长的 CLI 额外承担**战报主播**职责——监听链上事件流，把整场战斗过程渲染成文字实况发到群里。也就是说，「解说」不需要官方 Bot 也能存在，任何玩家都可以为自己的房间提供解说。
- **Keeper 模式**：CLI 可选开启 Keeper 循环——当「5 区块 / 15 秒」到期而无人手动结束时，由该 CLI（通常是队长的）自动调用 `advanceTurn()` 并支付该笔小额 gas。一个全员使用 CLI 的房间**不依赖任何官方基础设施**即可完整运转。
- **身份统一**：钱包地址与聊天账号绑定到同一个 `playerId`（绑定流程：Bot 下发一次性验证码，CLI 用钱包私钥对验证码签名回传验证）。同一 `playerId` 可随时混用「群聊指令（Bot 代发）」与「CLI 直发」两种通道。

#### 三层客户端并存架构（最终形态）

| 层 | 通道 | gas 谁付 | 费用模型 |
|----|------|----------|----------|
| L1a 纯聊天·免费档 | Discord / TG 群里发指令，官方 Bot 代发交易 | Bot 垫付 | **每日免费动作配额**（很小，官方随时可调；超出即拒绝代发）——获客成本，运营支出封顶 |
| L1b 纯聊天·充值档 | 同上，但玩家已向官方充值 CFX 或美元 | Bot 垫付（由充值覆盖） | **按动作计费**：单价 = 实测 gas × (1 + 服务费率)，公开价目表；Bot 链下账户余额扣减，余额不足拒绝代发 |
| L2 自托管 CLI | 本机 CLI + 自己的私钥 | **玩家自付 CFX** | 无任何平台费用，无配额 |
| L3 纯链上 | 任何钱包/脚本直接调合约 | 玩家自付 | 无（合约无许可，永远开放） |

**付费墙的合法性边界**：限制发生在 **Bot 通道层**（中心化服务，天然有权决定服务谁、收多少），不是链上层——游戏合约保持无许可，L2/L3 玩家不受任何影响。不付费玩家「被限制游玩次数」的具体形态就是 L1a 免费配额用尽后 Bot 停止代发；想继续玩有两条路：充值（L1b）或 CLI 自付（L2）。这直接满足商业目标：**官方对 L1a 的补贴被配额硬性封顶，L1b 用户的 gas 由自己支付，L2/L3 零补贴**。

官方 Bot 在此架构下退化为「L1 的代发器（含计费）+ 全局 Keeper 兜底 + 价格预言机」，而不再是游戏的必要组件——**游戏的核心运行只依赖链，不依赖官方服务器**，这与「纯区块链后端」的定位自洽。商业上，L1a 免费配额是获客漏斗，CLI 体验优化（一键安装、战报美化）持续引导用户向 L2 迁移。

#### 私钥安全要求
- CLI 不得以明文存储私钥：使用 keystore 文件 + 口令加密，或环境变量引用。
- 建议支持硬件钱包签名（Ledger 等 EVM 标准设备），CLI 只构造交易不接触私钥。
- 验证码绑定流程中，验证码必须由**钱包签名**而非私钥明文传输；验证码一次性、短时效。

### 2.2 状态建模与 gas 成本
- **最小化链上状态**：房间/角色/怪物 HP/魔素/技能计划属于「权威必须上链」的状态，放在合约 storage。
- **展示层走事件 + 索引器**：Bot 订阅合约事件，在群内渲染可读战报，避免每次查询全量链上读。
- **storage 优化**：角色属性可存为 `uint` 打包或 `struct`；技能计划用紧凑数组；房间数量设上限以控成本。
- **游戏币用内部账本而非 ERC-20**：因为禁止 P2P 转账且需支持负数，内部 `mapping(playerId => int256)` 最简单。

### 2.3 随机数（RNG）：可插拔、可配置、游戏级优先

#### 2.3.1 立场：两层随机架构 + 来源必须可配置

这是一个游戏，不是博彩协议。链上随机数按「单次价值 × 调用频率」切成两层（完整论证见 `randomness-design.md`）。**战斗内随机**（命中、目标、奖励、死亡召唤、效果概率）单次价值极低但调用频率极高，采用**房间级链式 PRNG**（伪随机数生成器，Pseudo-Random Number Generator）：以房间持久化种子为底，每次抽数混入 `PREVRANDAO` 并写回种子，形成确定性但不可预测的随机数链，单次成本约一次哈希加一次存储写。**创建层与高价值随机**（角色创建掷骰、掉落、未来的抽卡）单次价值高、操纵动机强，走 `RNGRouter`（随机数路由器）统一抽象，默认挂 `BlockEntropyRNG`，未来可平滑切换到可验证随机函数（VRF，Verifiable Random Function）。架构上有一条硬要求：**随机数来源必须可插拔、可由运营方配置**——任何场景都能在不改动核心合约逻辑的前提下，切换到更强或更弱的随机源。

#### 2.3.2 架构：战斗走房间级链式 PRNG，创建层走 IRNG 接口 + RNGRouter

战斗内随机**不经过 RNGRouter**，直接调用 `CombatTypes.nextRandom`（房间级链式 PRNG，见 `randomness-design.md` §2）——省去路由开销，且天然与房间状态绑定、保持单笔交易原子性。创建层与高价值随机仍通过统一接口向 `RNGRouter` 要随机数：

```solidity
interface IRNG {
    // 同步取数：立即返回一个基于上下文的伪随机数
    function next(bytes32 category, bytes32 context) external returns (uint256);
    // 异步取数（仅 VRF 类 provider 需要）
    function request(bytes32 category, bytes32 context) external returns (uint256 requestId);
}
```

`RNGRouter` 维护「用途 → Provider（随机源提供者）」映射，由管理员配置（未来可移交治理）：

| 用途 category | 覆盖场景 | 默认 Provider |
|---|---|---|
| `COMBAT` | **已退役**：战斗内随机改走房间级链式 PRNG（`CombatTypes.nextRandom`），不再经 RNGRouter 路由 | — |
| `AFFIX` | 角色创建随机：**种族抽取（三层加权 85/12/3）+ 词条随机（方向→词条→档位三次掷骰）** | BlockEntropy |
| `DROP` | 关卡通关道具掉落 | BlockEntropy |
| `MARKET` | （预留）市场类随机 | 按需 |

配置入口就是普通的 `setCategoryProvider(bytes32 category, address provider)` 与 `setGlobalProvider(address)`。每次切换通过链上事件播报，玩家可以审计当前每个用途实际用的是哪个随机源。可选玩法扩展：允许房主建房时为自己的房间选随机档位（例如「混沌模式」纯区块熵、「严肃模式」走 VRF），作为差异化玩法。

#### 2.3.3 内置 Provider 清单

| Provider | 类型 | 熵源 | 成本 | 信任假设 |
|---|---|---|---|---|
| **房间级链式 PRNG**（战斗默认） | 同步（有状态） | `keccak256(room.seed, roomId, turnId, PREVRANDAO)`，每次抽数写回 `room.seed` | 极低（一次哈希 + 一次存储写） | 验证人仅有轻微偏置能力；玩家无法预知所在区块的 PREVRANDAO |
| `BlockEntropyRNG`（创建层默认） | 同步 | `keccak256(blockhash(n-1), PREVRANDAO, block.number, block.timestamp, category, context)` | 极低（一次哈希，零存储写） | 验证人仅有轻微偏置能力 |
| `CommitRevealRNG` | 同步（跨回合） | Keeper 每回合先提交（commit）哈希，下回合结算时揭示（reveal）并入熵 | 低（每回合多一次存储写） | Keeper 无法「看到结果再决定」，扣发可见 |
| `KeeperPushRNG` | 同步 | Keeper 每回合直接推送种子 | 最低（随 `advanceTurn` 顺带写入） | 完全信任 Keeper |
| `VrfRNG`（可选） | 异步回调 | 第三方或自建 VRF | 高（两次交易 + 回调） | 信任 VRF 提供方 |

关键工程约束：**回合结算必须是单笔交易的原子操作**（见 §2.4）。房间级链式 PRNG 与同步 Provider 都能保证这一点；异步 VRF 会把一个回合拆成「请求随机数 → 回调 → 结算」三步，Keeper、Bot 与超时判定逻辑随之全部复杂化。这是「默认不用 VRF」最重要的技术理由——不只是省钱，而是保住回合结算的原子性。

#### 2.3.4 Conflux eSpace 链上熵源要点

依据 Conflux 官方 EVM 兼容文档（[evm-compatibility](https://github.com/Conflux-Chain/conflux-documentation/blob/main/docs/espace/build/evm-compatibility.md)）：eSpace 通过 Conflux 改进提案（CIP，Conflux Improvement Proposal）-645 对齐以太坊 EVM 行为；`BLOCKHASH` 可查询范围比以太坊更宽（近 256 块 100 gas，`[n-65535, n-257]` 区间 2100 gas）；`PREVRANDAO` 按以太坊语义可用；且 eSpace 上以太坊型交易只会被打包进高度为 5 的倍数的区块——这与「每 5 个区块一个回合」的节奏天然对齐。上线前需在测试网实测 `PREVRANDAO` 在 eSpace 的具体回填值，若语义存疑可退化为 `blockhash(n-1) + block.timestamp` 混合熵，代价仅为熵来源少一项。

#### 2.3.5 威胁模型：为什么「不安全」的随机数对本游戏够用

对三类潜在操纵者逐一分析。**验证人**：Conflux 采用树图结构权益证明（PoS，Proof of Stake）共识，单个验证人要对特定区块哈希施加偏置，需要在树图分叉中押对参考块，其成本远高于收益（收益不过是游戏里一次暴击或一条词条）。**中继器 Bot**：理论上可以「重掷」（re-roll）——观察到不利的区块哈希就暂扣交易、等下一个块再发。但 Bot 本来就是托管方案（§1.4 方案 C/D）的信任锚，它若要作恶，能做的事情远多于操纵随机数；且扣发会在群聊里表现为可观测的回合延迟，切到 `CommitRevealRNG` 档位可进一步压缩该能力。**自付钱包玩家**（Phase 2 模式）：玩家自己发交易时确实可以挑选发送时机，但结算熵混合的是**包含该交易的区块**的哈希与 PREVRANDAO——玩家在签名时并不知道这个值，无法预判结果，只能靠反复重发去「刷」，而这会被频控与动作费压制。

还有一个容易被误解的要点：**词条随机的真正风险不是「被预测」，而是「被重掷」**——玩家反复重建角色直到刷出极品词条。这是经济学问题而非密码学问题：VRF 同样无法阻止重掷，唯一有效的手段是让每次掷骰子都有成本（重建消耗道具、每日创建/入场上限、动作费），这些已在经济与风控设计中覆盖（见 §6 与 `gameplay-design.md` §7）。因此 `AFFIX` 用途默认也使用 `BlockEntropyRNG`，是威胁建模后的结论而非权宜之计。

### 2.4 战斗结算的确定性
- 合约内战斗必须**确定性**：给定（技能计划 + 行动顺序 + 魔素 + RNG 种子）产出唯一结果。
- 结算分两步更省 gas：**撮合（记录意图）→ 结算（回合结束时一次性计算）**，而非每个动作单独写链。

### 2.5 技能引擎：数据驱动的技能定义（承载复杂度 + 控制 gas 的核心）

技能需求非常复杂：无法手动选目标、单体/多体/全体攻击、**多段连击（一次行动 N 段独立随机目标伤害）**、我方治疗、**护盾（事件型）与伤害乘区（种族技限定）**、控制（眩晕若干回合）、自伤副作用、AP（行动点数）门槛与产出、魔素消耗、**弹药消耗（火枪手按发付费，读改道具数量）**、伤害上限、命中率惩罚（敌我/双方/绝对命中豁免）、怪物召唤（需读取战场状态）……这些**不写死在合约逻辑里**，而是全部**数据化**为统一的 `Skill` 结构，结算器只实现**一组有限的原语（primitive）**：

```solidity
struct Skill {
    uint32 id;
    uint8  kind;          // PHYSICAL / MAGIC / SUPPORT / SUMMON(怪物专用)
    uint16 apCost;        // 物理技：施放所需 AP（余额不足 → 失败空过）
    uint16 apGain;        // 物理技：命中后产出 AP（存入房间级角色 AP，跨战斗继承，§2.5.2）
    uint16 ammoId;        // 弹药类技能：消耗的道具类型 id（0 = 无弹药需求，哨兵值；道具 id 从 1 起编、id 0 永不分配，注册层校验）——余额在引擎内部账本（§2.7），非 ERC 余额
    uint16 ammoCost;      // 弹药消耗数量（ammoId ≠ 0 时生效；每次行动固定烧 N 发，与命中数无关，见 §2.5.2）
    uint32 manaCost;      // 魔素消耗；魔素池是**房间（整座地下城）级状态，跨战斗继承、不随单场战斗重置**（gameplay-design.md §5）
    uint8  targeting;     // 目标模式，见下表；targetCount 仅在 MULTI 模式生效，其余模式忽略
    uint8  weightMode;    // 随机权重模式：UNIFORM(均匀) / HP_DEFICIT_ALLY(治疗按血量亏空加权) / THREAT_ENEMY(按敌人威胁权重)
    uint8  targetCount;   // RAND_MULTI_*（不重复目标数）/ RAND_STRIKE_ENEMY（连击段数，≤8）
    uint64 power;         // 伤害/治疗基数（结算时乘属性、随机修正；中间计算 uint256）
    uint64 damageCap;     // 单目标单次伤害上限；0 = 无上限（仅管理员注册的破墙技可设 0，玩家不可获得无上限技）
    uint16 baseAcc;       // 基础命中率（千分比，注册时强制 ≤1000，默认 1000）——数值层可做「重击不稳」类设计，只降不升
    uint8  flags;         // 位掩码：bit0 = GUARANTEED_HIT（绝对命中：跳过命中掷骰，见命中判定管线）；bit1 = FLAG_MANA_ALL（耗光房间魔素池，伤害基数 = 本次消耗魔素量——爆裂魔法）
    Effect[4] effects;    // 固定长度，配 effectCount 使用（类型层防 DoS，注册时强制 count<=4）
    uint8  effectCount;   // 实际 effects 数量（0~4），结算只遍历前 effectCount 条
    SummonRule summon;    // 仅 SUMMON：读取战场的召唤规则
}

struct Effect {
    uint8  op;            // 见下方枚举表
    uint8  duration;      // 持续回合数（控制类），每回合递减
    uint16 magnitude;     // 数值
    uint8  scope;         // 作用目标（自己/被击者/全队/敌全体）
}

struct SummonRule {
    uint16 templateId;    // 召唤出的敌人模板
    uint8  maxCount;      // 单次召唤上限
    uint8  enemyHeadroom; // 场上允许的「敌人超出角色数」裕量（如 +2）
}

struct MonsterAI {
    uint16[8] skillCycle; // 技能循环表（按回合数取模查表；0 = 普攻占位；待机怪放「空技能」id）
    uint8  cycleLen;      // 循环长度（1~8）
}
```

> **conditionBits 已删除（用户定案的简化）**：旧设计的条件位掩码（「魔素低于 X 时跳过大招改普攻」）既占结构体字段又给 AI 执行器增加分支与结算 gas。替代：**怪物大招照常注册 `manaCost > 0`，魔素池干涸时在两阶段资源门槛的 Phase 1 自然检查失败、零扣减空过**（§2.5.2）——零新代码，且天然形成战斗后期的喘息空间：魔素耗尽后双方大招皆哑、回归白刃战。设计弹性无损：循环表本可自由编排普攻位。**怪物的随机抽/放魔素**由 MANA_DELTA 技能承担——需要随机性时给该 Effect 配 `prob` 字段（如 30% 概率抽毁，零新代码）；**「下回合生效」的延迟魔素操作被明确拒绝**（需要新增延迟效果队列原语，复杂度不值得）。**待机怪（魔素岩）无需专门待机模式**：注册一个 `power=0、effectCount=0` 的空技能放进 skillCycle 即可，引擎照常执行（无事发生）。

```solidity
struct EnemyTemplate {
    uint16 aiId;          // 关联 MonsterAI
    uint8  threat;        // 威胁权重（THREAT_ENEMY 模式下的抽取权重；Boss/召唤师设高值；1 = 与均匀等价）
    OnDeathSpawn onDeathSpawn; // 死亡召唤（波次战斗）：被消灭瞬间掷骰，命中则当场召唤新敌人、战斗不间断继续
    // … 属性等模板字段
}

struct OnDeathSpawn {
    uint16 templateId;    // 死亡时召唤的敌人模板
    uint8  count;         // 召唤数量
    uint16 prob;          // 概率（千分比；1000 = 必召；掷骰走房间级链式 PRNG）
    // 全零 = 无死亡召唤（普通模板不占额外逻辑）
}
```

**Effect.op 枚举首版**（可经合约升级追加，每个 op 的叠加/驱散规则随枚举定义固化）：

| op | 效果 | 叠加 | 可驱散 |
|----|------|------|--------|
| STUN | 眩晕：跳过行动。**含 `scope=SELF` 自施形态**——黑魔法师「爆裂魔法」的全体伤害配一条「对自己 STUN」的 Effect 即实现自晕（用户定案：删除原 SELF_STUN 专用 op，效果定向由 `Effect.scope` 承担） | 同名不叠加，取较长持续时间 | 是（DISPEL） |
| DMG_OUT_MOD | **伤害乘区·输出侧**：修正**自己造成的伤害**（`magnitude` 千分比，正=增伤）——仅狂暴（兽人）、龙鳞（龙人）两个种族技使用，见 §2.5.2 第 8 条复杂度审查 | 同 op 合并（magnitude 相加，duration 取 max） | 是 |
| DMG_IN_MOD | **伤害乘区·承伤侧**：修正**自己受到的伤害**（正=承伤增加，狂暴「以伤换伤」的代价面）——与 DMG_OUT_MOD 同为引擎**仅有的两个乘区 op**，替代已删除的 DEF_UP/DEF_DOWN | 同上 | 是 |
| SHIELD | **限时护盾**：`magnitude`=护盾量、`duration`=持续回合；伤害结算先扣护盾层（多层独立计时、各自倒计时）再扣 HP；到期未耗完直接消失；**多层扣减顺序 FIFO**（先挂入的先消耗）。**护盾量两种来源**：静态注册（盾墙/磐石之躯/岩石壁垒），或 **`power × 施放者属性` 结算后写入**（自选技「魔力护盾」吃魔攻系数——复用伤害/治疗的 power×属性既有结算路径，只是把结果写入护盾层而非 HP，零新原语，公式数值层定） | 多来源独立计时，不合并 | 是 |
| EVADE_UP | 回避提升（防御方侧的命中惩罚，见命中判定管线） | 多来源叠加，受全局命中下限保护 | 是 |
| ACC_DOWN | **命中率降低**（攻击方侧的命中惩罚，见命中判定管线）：`magnitude`=千分比惩罚、`duration`=持续回合；可由玩家技能/道具或怪物技能施加；作用于施放者的对立方——对敌单体/全体施加、或以 ROOM_ALL 烟幕同时施加于**敌我双方**（含施放者自己） | 多来源叠加，受全局命中下限保护 | 是 |
| GUAR_NEXT | **火枪手「鹰眼」**（红线的唯一豁口，`gameplay-design.md` §4.9）：作用于**自己**，施放时固定 `duration=2`（见下方时序）；期间自己的所有技能跳过命中掷骰。仅火枪手职业技可携带此 op（`SkillRegistry` 注册层校验：仅职业绑定技能表可配，自选池/道具/词条来源禁配）。已存在时**替换** duration（不累加） | 不叠加（已存在则替换持续时间） | 是（敌方 DISPEL 可剥鹰眼，是设计内的反制） — ✅ Move 已实现(命中豁免在 resolve 时读攻击方 op7；施放回合后下一回合生效) | 不叠加（已存在则替换持续时间） | 是（敌方 DISPEL 可剥鹰眼，是设计内的反制） |
| DOT | 持续伤害：**每回合开始结算**（`magnitude`=每跳固定值，不随属性缩放）——回合初先造成伤害（先扣护盾层再扣 HP，走正常伤害/死亡管线：DOT 致死会触发死亡召唤等既有结算），**再**递减 `duration`（次数 = duration；dur=3 → 3 跳）。**叠加规则（数值复审定案）**：同 op 反复施加时**只刷新 duration、不累加 magnitude**（否则持续上毒跳伤线性堆叠→任何怪被磨穿，毒刃 150×3 曾致平凡 1 级 100% 挖穿 D1）。毒刃为唯一现状使用者（20×3，随等级相对衰减，对低血目标有保底清场价值） | 同名刷新不累加 | 是 |
| HEAL | 即时/持续治疗 | 即时无叠加 | — |
| DISPEL | 驱散目标身上**标记为可驱散**的效果——对敌施放时剥增益（如 SHIELD、TAUNT），对己施放时净化负面（如 STUN、DOT）；驱散哪些方向由技能的 `targeting` + effect 配置决定 | 即时 | — |
| TAUNT | 嘲讽：被嘲讽者的**单体攻击**（`RAND_SINGLE_ENEMY`）随机目标强制重定向为嘲讽者；**多体/全体攻击不受影响**（防双坦吸干全部伤害，`gameplay-design.md` §4.8）；嘲讽者若出现在多体目标列表中则正常受击（不豁免）；**嘲讽者死亡时 TAUNT 立即失效** — ✅ Move 已实现(敌方单体攻击目标选择先扫描存活嘲讽者取最早者) | 互斥（后者覆盖） | 是 |
| LIFESTEAL | 吸血：按本次伤害的一定比例治疗施放者（恶魔种族技「汲魂」、嗜血词条） | 即时，随攻击结算 | — |
| MANA_DELTA | **魔素池操作**：`magnitude` 为正=注入（白魔法师「圣泉」、黑魔法师「献祭」**逐段**产出——多段技每段命中各结算一次，「战地血泵」的产魔面）、为负=抽毁（敌人「魔素泄漏」「魔素虹吸」）——操作的是房间级魔素池而非角色 | 即时 | — |
| STUN×P | 概率控制：Effect 概率字段 <1000 时结算掷骰（盾击眩晕、暴风术**每段独立**掷骰、缠绕束缚）；默认 1000=必中——复用 STUN/DOT 等 op + `Effect.prob` 字段（默认必发） | 同所附 op | 同所附 op |

**op 表删减注记（用户定案的简化）**：
- **SELF_STUN → 删除**，并入 STUN + `Effect.scope=SELF`（`Effect` 结构本就有 scope 字段——自己/被击者/全队/敌全体，无需新字段）。**唯一语义变化**：自晕从「不可驱散」变为继承 STUN 的「可驱散」——黑魔法师可用自选槽拿「净化术」自解爆裂魔法的自晕（净赚晕眩时长−1 个行动位的输出），或由队友驱散。这是有边界的配合深度而非漏洞（净化占一个行动位与技能槽），数值层用晕眩时长平衡；与「黑魔法师需要白魔法师续命」的职业配合哲学同向。
- **SILENCE → 延后注册**：首版内容零使用（查遍内容设计，无沉默系敌人技能；鹰眼的打断反制由 STUN 独立覆盖）。op 枚举本就「可经合约升级追加」——出现沉默系怪物时再回来注册，首版省一个死分支。

**内容层新增原语登记**（`content-design.md` §10，全部小~中等改动、不触碰三大架构红线）：① `Skill.hpCost`（黑魔法师「献祭」以命换多段攻击，与 AP/魔素/弹药同入两阶段门槛）；② SUMMON 扩展玩家侧（白魔法师「替身人偶」假目标：有血量、无行动、计入我方随机目标集稀释敌方命中、**不参与收益分配、不占玩家名额、无法嘲讽**、占房间单位总数上限——复用召唤槽预分配机制）；③ 上表 MANA_DELTA / LIFESTEAL / `Effect.prob`（圣泉=治疗+魔素注入的**一技能多效果**，由现有 Skill 结构承载）；④ **DMG_OUT_MOD / DMG_IN_MOD** 两个伤害乘区 op（狂暴、龙鳞——同时删除 DEF_UP/DEF_DOWN，见 §2.5.2 第 8 条审查）；⑤ 弹药道具两档（铅弹/龙击弹，`ammoId` 字段天然支持，ItemRegistry 多注册一种）；⑥ 复活原语（「不死鸟之羽」，预留、经济敏感可后置）；⑦ **死亡召唤 `EnemyTemplate.onDeathSpawn`**（模板 id + 数量 + 概率 `prob`，死亡结算掷骰复用既有召唤路径，§2.5.2 第 5b 条——实现红线：胜利判定在死亡召唤之后；用例 D5 炉毁概率召唤皇帝）；⑧ **变体敌人表 `BattleConfig.variantTables`**（开战一次掷骰按权重选敌人构成表，与周常变异选表同一落点；用例 D5 战斗 ③ 宝箱/皇帝双变体——宝箱=低血量待机怪，零专用流程）；⑨ **首角色免费重掷计数器 `Limits.freeRerolls`**（`playerId => uint8` 绑定计数器，防「新手福利道具化→工作室开号白嫖→重掷道具无限免费铸造」的女巫攻击链，`gameplay-design.md` §7.6 审查表；重掷入口资源检查二选一，重掷逻辑本身零变化）。**引擎 op 净变化 = +2 −4**（+2：DMG_OUT_MOD/DMG_IN_MOD；−4：DEF_UP/DEF_DOWN、SELF_STUN 删除 + SILENCE 延后——数据多、原语少）。另有 **MonsterAI.conditionBits 字段删除**（§2.5，魔素门槛由 Phase 1 资源检查天然承担）。

### 2.5.1 活跃效果（ActiveEffect）：运行时状态模型

`Effect[4]` 是**技能定义层**；技能命中后效果**落到角色身上**，运行时状态用独立的固定数组存储：

```solidity
struct ActiveEffect {
    uint8  op;            // 与 Effect.op 同一枚举
    uint8  duration;      // 每回合结算时 -1，归零即移除
    uint16 magnitude;     // 剩余数值（盾的剩余量 / DOT 每跳量等，按 op 语义使用）
    uint16 sourceId;      // 来源（技能/道具 ID，战报播报用）
}
// 存储于角色战斗状态内：ActiveEffect[6] effects（固定 6 槽，足够容纳 4 条技能效果 + 道具/词条来源）
// 满 6 槽时新效果被**拒绝**（该条 effect 落空，技能其余效果照常结算）——容量是类型层硬上限，保证回合遍历 gas 有界
```

- 结算顺序：每回合行动者结算前，先遍历自身 ActiveEffect 处理 DOT/倒计时；伤害结算时遍历 SHIELD 层（FIFO 扣减）；死亡时整组清除。
- **同 op 合并规则（可叠加类）**：`ACC_DOWN` / `EVADE_UP` 这类「多来源叠加」的 op，**同一角色的同一 op 只占一槽**——新来源施加时 `magnitude += 新值`、`duration = max(原剩余, 新持续)`。独立计时类（SHIELD、DOT）才各占一槽。由此 6 槽足以容纳「烟幕 + 致盲 + 道具」三重 ACC_DOWN（合并为 1 槽）+ 护盾 + DOT + 控制，不会被叠加惩罚挤爆。
- 每回合最坏遍历：≤10 角色 × 6 槽 = 60 次常数操作，gas 有界。

**targeting 模式与目标选择规则**（玩家只传技能 ID，目标一律由结算器决定；**不允许任何手动指定目标**）：

| 模式 | 目标选择规则（全部随机，按 `weightMode` 加权） | targetCount |
|------|--------------|-------------|
| RAND_SINGLE_ENEMY | 从存活敌人中**随机 1 个**（RNG 决定） | 忽略 |
| RAND_MULTI_ENEMY | 从存活敌人中**随机 N 个不重复** | 生效 |
| RAND_STRIKE_ENEMY | **多段连击**：N 段独立伤害实例，**每段独立抽取随机目标（可重复命中同一目标）**、独立命中掷骰、独立伤害上限——连射/乱舞类技能；`targetCount` = 段数（注册时硬上限，如 ≤8）；AP/魔素/弹药按**行动整体**扣一次，不按段数重复扣；effects 逐段独立施加（同 op 叠加遵循合并规则） | 生效 |
| ALL_ENEMY | 全部存活敌人（无随机性） | 忽略 |
| RAND_SINGLE_ALLY | 从存活我方（含自己）中**随机 1 个** | 忽略 |
| RAND_MULTI_ALLY | 从存活我方中**随机 N 个不重复** | 生效 |
| ALL_ALLY | 我方全体（含自己） | 忽略 |
| ROOM_ALL | **场上全体存活单位（敌我双方，含施放者）**——烟幕/天候类场地效果专用 | 忽略 |
| SELF | 自己 | 忽略 |
| MOST_WOUNDED_ALLY | **我方血量亏空绝对值最高者**（`maxHp − hp` 最大；满血跳过；并列取加入序最早；全员满血时施放者自己空转）——圣愈之光（天使种族技）的**确定性治疗指向**：线性扫描取 argmax，零 RNG 消耗（非排序——只要最大者不要全序） | 忽略 |

- **weightMode 加权随机**（默认 UNIFORM 均匀）：`HP_DEFICIT_ALLY` 按目标当前血量亏空加权（治疗技默认推荐——残血更可能被奶到但非必然）；`THREAT_ENEMY` 按 `EnemyTemplate.threat` 加权（Boss/召唤师更可能被打到但非必然）。加权抽取仍是**随机**，玩家不可指定；权重全 1 = 均匀。加权使治疗/输出的期望贡献可预估（排技能有决策依据），同时保留方差（戏剧性时刻）。
- 随机目标消耗 RNG 调用（走房间级链式 PRNG，见 §2.3）——目标随机性与命中/效果概率共享同一随机源体系，是「运气权重」（`gameplay-design.md` §3.1）的实现载体。
- **TAUNT 交互**：单位身上存在 TAUNT 效果时，其**单体攻击**的随机目标被强制重定向为嘲讽者（多体/全体不受影响；见 Effect 表 TAUNT 行）——唯一的确定性目标干预。
- 随机选择的 gas 成本：从 ≤10 个候选中加权抽取是 O(候选数) 的简单循环 + 一次 RNG，无 gas 风险。
- **收益随机分配**：结算时对每个存活者从 RNG 取随机权重，按权重瓜分奖池（`gameplay-design.md` §6.1）——同一结算交易内完成。

#### 命中判定管线（用户定案：命中修正**只降不升** + 绝对命中豁免）

结算器在**选定目标之后、结算效果之前**执行命中判定，规则固定为三层：

1. **豁免掷骰（以下四种情况直接命中，不消耗 RNG）**：
   - `targeting` 为我方系（`RAND_*_ALLY` / `ALL_ALLY` / `SELF`）——**对我方的治疗与增益永远绝对命中**（奶不 miss）；
   - `targeting` 为 `ROOM_ALL`——场地效果（烟幕等）必生效；
   - `flags.GUARANTEED_HIT`——技能固有的**绝对命中**（无视一切命中惩罚），配给少数特殊攻击技。
   注意：**绝对命中 ≠ 指定目标**——目标仍按随机规则选取（§4.2 原则不变），「绝对」只保证「选定后不会落空」；
   - 攻击者身上存在 `GUAR_NEXT` 活跃效果（火枪手「鹰眼」，见 Effect 表）——其**本轮所有技能**跳过掷骰。
   **GUAR_NEXT 时序（精确语义）**：鹰眼在回合 N 施放（施放即占行动位，当回合不再有该火枪手的其他行动）；`duration=2` → 回合 N 结算时递减为 1（仍存活）；**回合 N+1 全程有效**（期间其所有技能跳过掷骰）；回合 N+1 结算时递减为 0，移除。若火枪手在回合 N+1 被眩晕（跳过行动），该效果**自然浪费**（回合结束照常递减归零）——这是设计内的打断代价。
2. **掷骰判定（敌方系攻击技，逐目标独立掷骰）**：
   `命中概率 = baseAcc − Σ(攻击者身上 ACC_DOWN) − Σ(防御者身上 EVADE_UP)`，向下钳制到**全局命中下限**（配置常量，如 50‰，官方可调）——堆满惩罚也不会出现绝对打不中。
   「攻击者身上」指**本次实际行动的单位**，「防御者身上」指**本次被选中的目标单位**——ACC_DOWN 挂在谁身上谁开枪受罚，EVADE_UP 挂在谁身上谁更难被打中。
   每个目标一次 RNG 调用（房间级链式 PRNG，§2.3）；多目标技逐个掷骰，gas 上限 = 目标数 × 常数。
   **ROOM_ALL 烟幕的时序**：效果在施放者行动结算时立即挂到全体——按敏捷序，**先于施放者行动的单位不受本次烟幕影响，晚于施放者的单位本回合即受影响**；高敏捷施放者天然获得「先开枪再蒙烟幕」的时序优势，这是敏捷价值的组成部分（设计内，无需额外机制）。
3. **未命中的后果**：伤害与效果全部落空，但**已支付的 AP/魔素不退还**，物理技的 `apGain` 也拿不到（本就是「命中后产出」）——命中率惩罚的战术价值就是让敌人**白花钱空过**。
- **设计红线（引擎层固化，用户定案含唯一豁口）**：枚举中**不存在任何通用提高命中率的 op**；`GUARANTEED_HIT` 只能由技能注册时固有配置，**无法通过任何技能/道具/词条在战斗中获得**。命中经济学只有「变差」与「豁免」两态，没有「变好」——**唯一例外**：火枪手职业的 `GUAR_NEXT`（鹰眼，`gameplay-design.md` §4.9），它是职业本体而非通用增益，注册层强制四道闸：仅职业技能表可配、仅作用于自己、以行动成本付费（鹰眼回合无输出）、可被控制与驱散反制。实现上它是一个普通 ActiveEffect op + 命中管线一条豁免分支——代码并不脏，「脏」的只是红线上的这道刻意的口子。

#### 2.5.2 设计原则与各需求的落地方式

1. **不允许指定目标 → targeting 全随机（可加权）**：合约按 `targeting` 模式 + `weightMode` 从合法目标集合中抽取目标（RNG 决定，玩家不可指定），**玩家排技能时只需给技能 ID，无需给目标参数**，calldata（调用数据）极小，也天然杜绝「背刺残血挂机队友」类指令歧义；随机目标是运气权重的核心载体（`gameplay-design.md` §3.1）。
2. **AP / 魔素 / 弹药三重门槛（两阶段模式，实现红线）**：**Phase 1 只读检查**——`apCost` vs 角色 AP、`manaCost` vs 房间魔素池、`ammoId≠0` 时引擎**内部账本的弹药余额** vs `ammoCost`（§2.7）；**Phase 2 全部通过后才依次扣减**——AP（**房间级角色状态——用户定案：AP 跨战斗继承、不再每场重置**；字段随生命/金库同存于房间级角色状态，加入房间时初始化为 0，战斗切换**零处理**——战斗开始的逐角色 AP 清零写被整体删除，这也是本改动的代码简化面）、魔素（房间池）、弹药（内部计数器 −N，掉落即「铸造」进账本、消耗即核销）。**任一不足则零扣减、失败空过**（写一个事件即可）。三项资源**全部位于引擎自身 storage**——检查与扣减都是本地 SLOAD/SSTORE，**无任何跨合约调用**（这比原 ERC-1155 钱包直扣方案更快，两阶段红线也更易满足）。**弹药在扣减时即核销，之后即使 miss 也不退还**（与 AP/魔素同语义：枪响子弹就没了）。**词条层的静态资源修正（`content-design.md` §6.5，零新原语）**：资源词条创建时写入角色静态字段（`manaDiscount`/`apDiscount`/`apBonus`/`manaGainBonus`），Phase 1/2 各做一次 `max(0, cost − discount)`——opcode 级改动；`apBonus` 挂在每回合行动者结算前的既有 ActiveEffect 遍历同一循环；`manaGainBonus` 在玩家加入房间时**一次性聚合**为房间级缓存，每回合魔素增量结算时一次 SLOAD 加总——无逐回合全员词条遍历，gas 零边际。
   - 弹药余额与扣减都在**引擎内部账本**（§2.7）——同交易内的 `giveItem`（递弹药）按标准交易顺序生效：同区块先到的递弹交易先入账，本回合结算即用得上。
   - **左轮弹雨语义（消歧）**：`ammoCost=N` 表示**每次行动固定烧 N 发**，与命中目标数无关（命中 3 个还是 0 个都烧 N 发）；**不存在「逐目标逐发消耗、中途弹尽」模式**——弹尽即整次行动在 Phase 1 失败空过。
   - **计划条目推进 ≠ 资源扣减**：弹尽/资源不足空过时，`SkillPlan` 队列指针照常推进（该回合条目被消费、指针 +1 取模回到队首），但三种资源零扣减——空过是「技能效果落空」，不是「排技能失败」。
   - gas：三重门槛全部本地 SLOAD/SSTORE，合计 < 1 万 gas/行动，**比 AP/魔素本身还便宜**（原 ERC-1155 钱包直扣方案的跨合约调用已消除）。
   - **递弹药（弹药不是房间状态）**：任何人可随时 `giveItem(火枪手, 子弹id, N)`——引擎**内部账本转账**，一笔极便宜交易，不占任何人的行动位、无需对方操作（§2.7）——「给火枪手递子弹」是设计内的社交协作（`gameplay-design.md` §7.2）。
3. **伤害上限**：`damageCap` 钳制**基础伤害**（`power × 属性` 之后、乘区之前 `min(base, cap)`）——**乘区加成（狂暴/龙鳞的 DMG_OUT_MOD/DMG_IN_MOD）可突破单次伤害上限**（用户定案：种族技的增伤/承伤不应被 cap 压死；钳制先于乘区，`damage = min(power × 属性, cap) × (1+ΣDMG_OUT_MOD) × (1+ΣDMG_IN_MOD)`），同时给了打包空间——HP 与伤害都可用 `uint64` 以下整数存储，**一个 `uint256` slot 打包多个战斗字段**。**多段连击技的每段独立钳制**（`RAND_STRIKE_ENEMY`，N 段 × 每段上限 = 总输出上限，段数由注册时 `targetCount` 封顶 ≤8）。
4. **召唤读取战场**：结算器在执行 `SUMMON` 时数一遍存活敌人数 E、存活角色数 P，若 `E >= P + enemyHeadroom` 或达房间单位总数上限则**召唤落空**；否则召唤 `min(maxCount, P + enemyHeadroom - E)` 个。全程只有计数循环，无额外存储。
4b. **死亡召唤（OnDeathSpawn，波次战斗）与变体敌人表（variantTables）——同场新敌与开战掷骰的结算实现**：
   - **死亡结算分支**：任何单位 HP 归零时，死亡结算顺序固定为 **① 标记死亡（释放槽位与增益）→ ② 若为敌人且带非零 `onDeathSpawn`：掷骰（一次房间级链式 PRNG）→ 命中则按既有召唤路径（槽位预分配、敌人 ≤10 上限、上限冲突跳过并播报）当场实例化新敌人 → ③ 才判定战斗胜利（敌人全灭）**。②未命中或上限落空则直接进 ③——胜利判定**必须**发生在死亡召唤之后，否则出现「刚宣布胜利、皇帝又冒出来」的矛盾状态（实现红线）。死亡召唤复用 `SUMMON` 的既有路径与上限保护，新增代码仅一次掷骰 + 一次条件调用；gas 由敌人上限天然封顶。
   - **变体敌人表**：地下城配置里每场战斗的敌人表可为「单表」或「变体表数组 + 权重」；战斗初始化路径（队长发指令进入下一场 / Keeper 推进）在实例化敌人前，若配置了变体则**一次掷骰（房间级链式 PRNG）按权重选表**，其余初始化逻辑零变化——与周常变异的「按周确定性选表」（`gameplay-design.md` §3.4）共用同一落点，只是选择来源不同。**待机宝箱即低血量待机怪**（`skillCycle` 全空技能——魔素岩同款，§2.5 待机注记），「宝箱战」不需要任何专用流程或状态机旁路；掉落走模板掉落表照常。
   - **可选联动位 `bossSpawned`**：死亡召唤掷骰命中时置 1（房间状态一个 bit，与既有房间标志位打包同 slot）；变体掷骰读到该位时切换权重表（数值层保证「Boss 必现」的校准开关，默认关闭，`content-design.md` §8.1）。
5. **控制/增益（眩晕、护盾、回避）**：都是 `Effect` 列表里的 `op`，带 `duration` 递减；行动前先扫一遍自身 Effect 列表决定是否跳过（眩晕）。**每个技能的 effects 数量硬上限（例如 ≤4）**，保证单次结算 gas 有界。
6. **怪物技能**：怪物同样是 `Skill` 的消费者。怪物 AI（人工智能）不写代码，数据化为**技能循环表**（如 [普攻, 普攻, 召唤, 大招] 循环 + 少量条件位），结算器按回合数取模查表。
7. **伤害乘区与属性修正的复杂度审查（用户定案：避免临时加减防御力的技能）**：
   - **两种效果范式**：事件型 op（STUN/SHIELD/TAUNT/ACC_DOWN/EVADE_UP/DOT/LIFESTEAL/MANA_DELTA/SUMMON）改变**离散事件**——每个 op 的结算逻辑独立封闭、互不组合，新增事件型技能对结算器是**零改动**（纯数据注册）；其中命中系（ACC_DOWN/EVADE_UP）走**纯加法管线**（`命中率 = baseAcc − ΣACC_DOWN − ΣEVADE_UP`，一次槽遍历加总），是最廉价的一类。属性修正型 op 修改伤害公式的**连续乘区**——单个实现是小改，但复杂度**随使用数量超线性增长**（叠加语义矩阵「取最大/相加/相乘/覆盖」要逐 op 定义并测试，组合数平方级；若再分物攻/魔攻修正则 op 与公式分支翻倍；与静态词条乘区的顺序交互要专门定义；战报每次伤害要播报完整乘区链，gas 与可读性双降；数值校准工作量同步平方级膨胀）。
   - **结论：少量可控，大量显著复杂**。采纳避免方向——引擎只保留 `DMG_OUT_MOD` / `DMG_IN_MOD` 两个**通用伤害乘区 op**（删除 DEF_UP/DEF_DOWN），**修正伤害而非修正属性**：伤害公式统一乘区（`damage = min(power × 属性, damageCap) × (1+ΣDMG_OUT_MOD攻方) × (1+ΣDMG_IN_MOD守方)`——**钳制先于乘区**，乘区加成可突破单次伤害上限，§2.5.3 第 3 条），不区分物理/魔法——实现为结算时遍历攻守双方 ActiveEffect 槽位加总后各一次乘法（O(12) 常数遍历，gas 可忽略）。
   - **内容层封顶**：乘区 op 的使用者**仅 2 个种族技**（狂暴=OUT正+IN正；龙鳞=SHIELD+OUT正），种族技数量被种族数硬性封顶，乘区语义规模天然有界；**职业技能与自选池零乘区技**——防御面统一 SHIELD（事件型先扣层：磐石之躯已从减伤改为护盾），命中面统一 ACC_DOWN/EVADE_UP（加法管线：守卫「回避」只提回避，黑幕/深渊低语/尘幕同理）。设计表达力几乎无损（「变硬」=护盾、「变闪」=回避、「削弱敌人」=命中率惩罚），损失的只有「百分比减伤」手感（由护盾的等效吸收近似），换来乘区语义的规模上限与校准成本的大幅收窄（内容侧分析见 `content-design.md` §10.1）。

#### 2.5.3 gas 预算的量级论证

| 项 | 成本来源 | 约束 |
|----|----------|------|
| 单回合结算 | 遍历在场单位 × 每人 1 技能 × ≤4 effects | 在场单位上限（角色上限 + 敌人上限，建议双方各 ≤10）→ 最坏 ~25 单位 × 常数运算 + 少量 SSTORE（血量/魔素/AP 变更），估算 300k~800k gas |
| 排技能 | 1~2 个 SSTORE（计划打包进 slot） | 前瞻 N ≤ 16，每回合技能 ID 用 uint16 编码后 16 个也只占 1 slot |
| 召唤 | 复用预留的敌人槽位（房间创建时按敌人上限**预分配**数组），无动态扩容 | 敌人槽位预分配，召唤只是「激活已预留槽位」，避免运行时扩容数组的昂贵 SSTORE |
| 事件输出 | 每行动 1 条事件 | 战报细节放事件（链下 indexer 渲染），不占 storage |
| 命中/目标 RNG | 最坏约 200 次 RNG 调用/回合（10 单位 × 最多 8 段连击 × 每段目标抽取 + 命中掷骰 + 收益分配） | BlockEntropy 是纯视图逻辑（keccak256，无 SSTORE），单次约 30 gas，合计 < 7k gas，可忽略；miss 路径提前终止，实际通常远低于最坏值 |
| 弹药消耗 | 引擎内部账本 SLOAD/SSTORE（无跨合约调用） | < 1 万 gas/行动，比 AP/魔素扣减更便宜；弹尽空过只写事件，最便宜 |

事件中命中类动作附带 `guaranteed` 标志位（来源 = GUARANTEED_HIT / GUAR_NEXT / 我方系豁免），indexer 据此在战报中区分「鹰眼命中」与普通命中。

结论：最坏回合结算远低于 eSpace 单块 3000 万 gas 上限的一半，且有硬上限保证**不会因召唤失控或房间人数而 gas 爆炸**。

#### 2.5.4 可扩展性
- 新技能 = 在 `SkillRegistry` 里**注册一条新数据**，不改结算器代码。
- 新效果类型 = 给 `Effect.op` 枚举加一个原语（小改，走合约升级）。
- 结算器保持小而可审计，复杂度被「数据多、原语少」的原则封在配置层。

### 2.6 技能计划（SkillPlan）：前瞻排程的链上表达

「排技能」不是聊天口述，而是**明确的链上状态**。每个角色在房间内的计划用固定长度结构存储（**杜绝动态数组**），作为 `RoomMember` 的内联字段（与 AP/魔素等房间级角色状态同层，`CombatTypes.RoomMember`）：

```solidity
struct RoomMember {
    // ... 既有字段 ...
    uint16[16] plan;    // 前瞻队列（固定 16 槽，杜绝动态数组）
    uint8   planLen;    // 实际长度 0~16（前瞻 N ≤ 16 硬上限）
    uint8   planStart;  // 环形首指针：消费后 +1 取模，不真实移位，省 SSTORE
}
// plan 打包占 2 个 slot，planLen/planStart 挤进相邻字段，覆盖写只花 ~2 SSTORE
```

**生命周期语义（全部在合约层强制）**：
- **提交/覆盖**：`setPlan(uint16[16], uint8 len)` 一次性覆盖整条队列——玩家改计划永远是「以新换旧」，无增量 patch 歧义；提交者必须是角色拥有者（**只能给自己排**，队长也不例外）。
- **无限循环消费（用户定案）**：`advanceTurn()` 结算时按行动顺序取每个角色 `plan[planStart]` 执行；执行后 `planStart = (planStart + 1) % planLen`——队列走完自动回到队首，**无限循环使用玩家安排的技能序列**，不会因队列耗尽而停手。想改变行为就重新 `setPlan` 覆盖整条队列（例如把「输出循环」换成「攒 AP 循环」）。空过（资源不足）时指针照常推进，语义见 §2.5.2 第 2 条。
- **取消**：`cancelPlan()` 把 `planLen` 置 0——只支持**整体取消**，不支持部分取消（规则从简；要改就重新提交完整队列）。
- **执行不校验前置状态（设计内）**：队列执行时**不检查**前置效果是否仍有效——火枪手排「鹰眼 → 弹雨」两步计划后，若鹰眼被 DISPEL 剥掉或开火回合被眩晕，队列中的射击技仍照常执行（可能 miss 或空过）。计划是对未来的**承诺而非保证**，被拆解的风险由玩家自行评估——这正是「混乱与运气是乐趣核心」在排程层的体现（`gameplay-design.md` §4.3）。
- **回合快照**：`advanceTurn()` 的交易内计划消费以**该交易执行时刻**的链上状态为准；同区块内先到的 `setPlan` 生效、后到的下回合生效（区块内交易顺序即最终顺序，无歧义）。
- **道具使用（用户定案）**：作为特殊「技能 ID」（保留段，如 id ≥ 0xF000）排进同一队列，结算时转给道具逻辑——**使用道具占用该回合的行动位，用了道具当回合就不能再使用技能**（一个队列管一切行动）；**不限每场战斗的使用次数**（`gameplay-design.md` §7.2 定案：次数不限制，代价是占行动位——回合数本身就是天然上限）。
- **怪物无队列**：怪物不吃 SkillPlan，按 `MonsterAI.skillCycle` 取模行动（§2.5）。

### 2.6.1 Move 重写注记：技能计划的归属与拥有权校验（当前实现）

> 说明：§2.5/§2.6 的 Solidity 示意为迁移前版本；本小节以当前 `aptos/sources`（Move）实现为准，
> 并将代码中的**技能归属红线**显式记录于此。其余章节（RNG/菜市等）已在 Move 版另行落点，本节不重述。

**红线（用户定案）**：玩家可使用的技能**只来自职业、种族、自选池三个来源**（`content-design.md` §2.5 / §4 / §5）——
不存在任何其他来源（无等级解锁授予、无初始白送基础技、无 GM 隐藏渠道）。该红线在两处强制执行：

1. **创建端（`character.merge_skills`）**：技能权威源 = `Character.skill_ids`，**存于角色自身存储**（不复制进房间成员，
   避免每个成员冗余一套技能集 → 省 gas）。自选池挑选（`self_select`）逐 id 校验必须 ∈ **自选池白名单**
   （`skill_registry.pool_skills`，由 `content_registration` 显式登记 content-design.md §5 的十技：
   尘幕/毒刃/一闪/暴风剑/急救包扎/致盲粉/岩石壁垒/魔力护盾/龙息/魔爆术）；职业技、种族技、基础技与占位技、
   以及全部敌技（1000+ 区）**一律不在池内**，自选即拒绝（`abort E_SKILL_NOT_POOL`）。职业技/种族技由官方内容注册
   （`register_class_skill` / `race_def`）注入，视为可信来源。
2. **执行端（`engine.set_plan` / `cancel_plan`）**：房间成员 `Member` 携带 `owner: address` 与 `char_id: u64`（不复制技能）：
   - **只能给自己排**：提交者必须等于 `member.owner`（队长也无效，`gameplay-design.md` §4.3 的链上强制落地）；
   - **只用自己拥有的技能**：`char_id != 0` 时，提交的整条计划逐 id 校验 ∈ `Character.skill_ids`，否则 `abort`
     （敌技 45+、他人职业技等一律无法进计划）；校验发生在**提交时刻**（一次性，
     `O(len(plan) × len(skills)) ≤ 16×10` 次比较），回合执行 `advanceTurn` **零额外校验**（信任提交时校验）→ gas 友好；
   - `char_id == 0` 是 **`#[test_only]` 面板通道**（蒙特卡洛仿真 `sim.move` 与引擎单测直接注入裸面板，
     不进任何玩家路径）；**生产唯一入口 = `engine.join_room_as_char`**（校验角色归属 + 绑定 `owner/char_id`，
     从 `Character` 拷贝当前属性）。
- 怪物侧无此问题：AI 的技能循环直接引用注册表敌技（§2.5.5），与玩家拥有权无关。

### 2.6.3 Move 经济闭环与逃离注记（2026-09-30 实现）

对齐 `gameplay-design.md` §3.2 / §6.1–§6.3；此前这几条只有文档、引擎零实现（审计 A 类）。

- **余额有符号**：`economy` 账本为 `Table<address, i128>`。**救援费允许扣成负数且无上限**（§6.3/§10-13）；
  收益入账 `credit` 直接加到有符号余额上，因此**天然「先自动偿债、剩余才形成可支配余额」**。
  其余消费（`spend`、入场费）仍要求余额充足；`is_debtor` 供后续门控（负债者不得开房/购物/付费入场）。
- **入场费**：`engine::create_room` 按难度配置扣队长 Char，**直接销毁**（水槽）；余额不足整笔回滚。
- **收益发放**（§6.1，仅两个触发点）：① 通关整座地下城；② 队长在**战斗获胜后的间歇期**发起全员逃离
  （`engine::leader_retreat`）。对每个**存活且未逃离的玩家成员**独立抽取随机权重（1..=1000）按权重分奖池，
  余数归最后一人以保证账目守恒；无人可领（全灭/全逃离）则整池作废（`RewardForfeited`）。
- **救援费**（§6.3）：全队被击败或单场超时 → 对每个**仍在局内**的玩家成员按难度固定费扣款（含阵亡者）；
  **已个人逃离者与召唤物不扣**。败北判定以「是否还有存活且未逃离的玩家成员」为准——
  替身人偶活着不算玩家在场（§3.2）。
- **个人逃离**（§6.2）：`engine::request_escape`。战斗进行中 → **延迟 `ESCAPE_DELAY=3` 回合**离场
  （回合初结算）；战斗间歇期 → **立即离场**。离场者无收益、不再参战、不占活人名额、**免救援费**。
- **队长继承**（§3.2/§6.2）：个人逃离、阵亡或大厅退房后由 `ensure_leader` 自动继任——
  按 `members` 向量序（= `push_back` 加入序）取第一个**在场玩家**，**跳过召唤物**；无人可继任则不变更。
  离开房间（`leave_room`，仅大厅期）现在真正移除成员并触发继任。
- 新增视图：`room_leader` / `member_escaped` / `member_escape_delay` / `economy::balance_of`（i128）/ `is_debtor`。

### 2.6.4 Move 行动顺序与逐段目标注记（2026-09-30 实现）

对齐 `gameplay-design.md` §4.2；此前实现是「玩家固定先动、速度不参与排序」，多段技是「选定一个目标连击 N 段」。

- **敏捷降序行动**（`engine::action_order`）：每回合把全体在场单位（玩家 + 敌人）按 `speed` 降序排列后依次行动。
  实现为打包 key = `speed × 64 + priority` 的**插入排序**（n ≤ 20，O(n²)，无额外存储结构）：
  priority 玩家 = `40 − idx`（31..40）、敌人 = `20 − idx`（11..20），两段互不重叠且可反解。
  **同速时玩家优先**，同侧按索引升序。替身人偶（召唤物）不行动、不进序列。
  行动时重新确认存活（先手可能已把后手打死）；眩晕者跳过。
- **逐段独立随机目标**（`resolve_skill`）：`targeting == 3` 的多段技**每一段各自调用一次目标抽取**
  ——可能重复命中同一目标、也可能分摊给多只敌人；每段独立命中掷骰、独立享受伤害上限（§4.2 原文语义）。
  AP/魔素/弹药仍按**行动整体**只扣一次。
- **影响面**：`speed` 此前从未参与任何计算，敌人模板的 speed 值（D2 的 45~90 等）从未被校准过；
  上线后慢速面板（例：守卫×巨人的 1 级极限面板 spd 27）会**后手**，控制类敌人（缠绕眩晕）先落地。
  相关 sim 标定已按新引擎重跑（`sim_d2_l1_talented` 等）。

### 2.6.5 Move 入场次数门控与掉落注记（2026-09-30 实现）

> ⚠️ **本节的「入场次数门控」部分已被 §2.6.14 取代**：挑战券 / 每日挑战券与「额度优先扣」的账本已删除，
> 改为 24 小时滑动窗口且所有难度都计次。**掉落表部分仍然有效**（仅从中删掉了挑战券条目）。
> 保留本节作为当时的实现记录。

对齐 `gameplay-design.md` §7.2（此前挑战券账本存在但**没有任何门控读它** → 空转道具）。

- **入场次数门控**（`use_item::EntryGate`）：`daily_limit`（默认 **3 次/自然日**，GM 可用
  `set_daily_limit` 改，数值层参数无需改代码）+ `entry_day` / `entry_count`（按 `timestamp::now_seconds()/86400`
  的自然日粒度计次）+ `credits`（挑战券/每日券兑出的额外额度）。
  `engine::create_room` 对 **`entry_fee > 0` 的付费图**扣一次机会：**先扣 credits**（突破当日限制），
  再计当日次数，超额 `abort E_NO_ENTRIES`。**免费图不消耗次数** —— 这是为保 §6.3「负债者仍可进免费图打工」
  的显式取舍（文档 §7.2 未区分，此处按 §6.3 的硬承诺处理）。
- **掉落表**（`item::DropStore`）：`difficulty → vector<DropEntry{item_type, weight, amount}>`；
  `item_type = 0` 的条目代表「空手而归」。注册入口
  `item::register_drop_table(account, difficulty, item_types, weights, amounts)` 用**三条并行原始向量**
  （Move entry 交易不支持结构体参数），因此**上线后 GM 仍可一笔交易调整掉落**。
  结算时（通关 / 队长全员逃离）对**每个存活者**独立掷一次（`item::pick_drop`，seed 取自房间 RNG 流）。
- 初始掉落表（D1–D9，初值）：D1 魔素礼花；D2–D3 铅弹/疗伤药水；D4–D5 龙击弹/烟幕弹/生命之泉；
  D6–D7 生命之泉/挑战券/不死鸟之羽；D8–D9 挑战券/不死鸟之羽/命运骰子/重生卷轴。

### 2.6.6 Move 加权目标 / 效果作用域 / 双修与护盾缩放注记（2026-09-30 实现）

对齐 `gameplay-design.md` §4.2 与 `content-design.md` §5；此前 `weight_mode` 与 `effect.scope` 两个字段
**注册层写了、引擎从未读取**，导致治疗是纯随机、敌人威胁无意义、致盲粉的"双刃"无自降。

- **权重随机**（`engine::select_targets`）：候选池按 `skill.weight_mode` 赋权后加权抽取，
  **多体技能抽 N 个不重复目标**：
  - `WT_UNIFORM(0)` → 权重 1（默认，等价均匀）；
  - `WT_HP_DEFICIT_ALLY(1)` → 权重 = `maxHp − hp + 1`（残血更容易被奶，**满血也可能被抽中**，§4.2 原文）；
  - `WT_THREAT_ENEMY(2)` → 权重 = `threat + 1`（Boss/召唤师更易吃刀但不保证，小怪也可能中）。
- **效果作用域**（`effect.scope`）：`SCOPE_SELF(0)` 作用于**施放者本人**，其余作用于选中目标。
  这让「单体 + 自减益」这类双刃技能可在一条效果表内表达——致盲粉（860）=
  `RAND_SINGLE_ENEMY` + 两条 `ACC_DOWN 450`（一条 `SCOPE_SELF`、一条 `SCOPE_TARGET`）。
- **护盾缩放**：`OP_SHIELD` 在 `kind == MAGIC 且 power > 0` 时，护盾量 = `power × 魔攻 / 1000`
  （魔力护盾 880）；否则用效果条的固定 `magnitude`（岩石壁垒 870）。
- **双修伤害公式**：新增 `KIND_HYBRID(5)` —— 伤害按 `power × (ATK + MAG) / 1000` 结算（火枪手子弹：
  左轮弹雨 620 / 龙击弹 630，power 取原物理值之半以保持同量级）。
- **池技语义对齐**（§5）：急救包扎 850 由"确定性最重伤者"改为 `RAND_SINGLE_ALLY` + HP 亏空加权
  （确定性只留给天使种族技圣愈之光 760 的 `TGT_MOST_WOUNDED_ALLY`）；岩石壁垒 870 由"全体 ally"
  改回**自施**小额固定盾；魔力护盾 880 由"全体固定 850"改回**自施**且吃魔攻。
- 新增视图 `enemy_template(room_id, index)`（测试/展示用：该槽位由哪个模板实例化）。

### 2.6.7 Move 升级 / 角色转移 / 履历注记（2026-09-30 实现）

对齐 `gameplay-design.md` §2.4 与 §7.4（此前只有 GM 设级，无升级/转移/履历）。

- **升级**（`character::upgrade_level(account, char_id, levels)`）：**只消耗游戏币、无其他门槛**（§2.4）。
  费用 = `Σ(100 × 新等级)`（初值，数值层可调）；等级封顶 `MAX_LEVEL=300`；升级后按公式重算属性。
  走 `economy::charge_entry`（**严格扣款**）→ **负债者无法升级**（§6.3）。词条与已选自选技不受影响。
- **角色转移**（`character::transfer_character(account, char_id, to)`，§7.4）：与价格无关的规则在转移函数内
  100% 强制 —— ① **等级重置为 1**（属性同步重算）；② **关卡内（`room_id != 0`）禁止转移**
  （`E_IN_ROOM`）；③ 种族/词条/职业/自选技/**履历**随角色完整转移；`owner_chars` 索引同步迁移
  （买家 `owner_latest_char` 指向该角色）。不可强制的只有按成交价抽税（本设计不依赖）。
- **角色锁**：`engine::join_room_as_char` → `character::lock_room(char_id, room_id)`；大厅退房 / 个人逃离 /
  关卡结算（通关·败北·超时·全员逃离）都会解锁并记履历。
- **履历**（§2.4，纯荣誉、无数值）：`runs`（参与关卡数）/ `clears`（通关次数）/ `best_difficulty`
  （最高通关难度），`#view get_history`。**逐项统计（击杀/治疗量/被救援次数）需要引擎按伤害归属回写**，
  当前先记「参与/通关/最高难度」三项，其余列为后续。

### 2.6.8 Move 周常变异 / 中途加入 / 召唤缺口注记（2026-09-30 实现）

- **周常变异（§3.4）**：`engine` 维护 `week → Mutator{kind,value}`（`week = timestamp / 604800`），
  GM 用 `set_weekly_mutator(account, week, kind, value)` 按周配置；**创建房间时快照当周变异**
  （周中变更不影响已建房间），`#view room_mutator` / `current_mutator` 可查。落点全部是既有管线的**一个参数位**
  （§3.4「只采纳便宜实现」）：`MUT_MANA`(每回合魔素增量 +value) / `MUT_FOG`(敌人命中 −value‰) /
  `MUT_STORM`(多段技 +value 段, 封顶 `MAX_STRIKES=8`) / `MUT_HP`(敌人生命 ±value‰, 带符号) /
  `MUT_DROP`(value>0 额外掉落掷骰次数、<0 完全不掉落)。**每周一条、互不叠加**。
- **中途加入延迟到场（§4.5-5）**：`join_room*` 现在也接受 `phase == 1`（战斗进行中）；
  此时新成员带 `arrive_delay = JOIN_DELAY(3)`，**倒计时归零前不行动、不可被选为目标、不算「在场玩家」**
  （败北判定/队长继承/收益/召唤计数的口径一致）。间歇期或大厅加入 → 立即到场。
  新视图 `member_arrive_delay`，事件 `MemberArrived`。
- **召唤缺口公式（§4.5-1）**：敌方召唤技能**先读场上存活数**——存活敌人数 < 存活角色数 + 2 时，
  召唤 `min(缺口, 技能召唤上限)`；否则本次落空。这从机制上封顶敌人数量（此前召唤无上限、可无限膨胀）。
- **连带标定**：缺口公式封顶了 D5「督军增援」的兵源（原本可无限补哨兵），D5 near-max solo 由 86.7% 升到 95%；
  已回调 D5 敌值（机神哨兵 atk 2950→3400、机神魔像 3800→4200、机神督军 4000→4600），回到 **51/60 ≈ 85%**。

### 2.6.9 Move 回合驱动防护注记（Keeper，2026-09-30 实现）

对齐 `technical-design.md` §3 / §3.1（此前 `advance_turn` 是一个无防护的公开入口）。

- **同一入口**：自动（Keeper）与手动（任何队员/队长）都调 `advance_turn(account, room_id, expected_turn_id)`。
- **turnId 单调互斥**：`expected_turn_id` 必须等于房间当前 `turn_id`——同一回合只有**第一笔成功交易**
  能推进，并发/重放的后来者在 `E_TURN_MISMATCH(24)` 上失败且**状态零变更**（只浪费调用者自己的 gas）。
- **推进冷却**：距上次成功推进 ≥ `TURN_COOLDOWN_SECS = 2` 秒（§3.1「≥ 2 区块」的墙钟等价物），
  否则 `E_ADVANCE_COOLDOWN(25)`——任何人（含恶意 CLI）都无法高频刷推进。手动提前结束**不受「等满 5 区块」
  约束**（那是玩法特性），但同样受冷却约束；推进后计时基准重置。
- **Keeper 单点故障兜底**：`emergency_advance(account, room_id)` 在距上次推进 ≥ `EMERGENCY_SECS = 30` 秒时
  **任何人**都能调用（只推进一回合与超时判定，无任何特权）；正常节奏下门槛不可达。
- **超时判定随推进执行**：回合上限清退仍内嵌在推进路径（`check_end`），无需单独触发器。
- 辅助视图 `advance_ready(room_id)`（距上次推进是否已过冷却）。
- **客户端/Keeper 注意**：调用方需先读 `room_turn(room_id)` 再带进 `expected_turn_id`。

### 2.6.11 Move 复审修正注记（2026-09-30 架构 × 代码复审）

### 2.6.12 Move 房间回收注记（2026-09-30 实现）

对齐 `gameplay-design.md` §3.1。此前 `RoomStore.rooms` **只增不减**：房间关闭只置 `closed` 标记，
战斗结束后房间永久留在表里，`MAX_ROOMS` 也已因「代码里根本没有上限」而删除。本小节把房间变成
**可回收资源**，并顺手补上「关房不解角色锁」的缺口。

- **终态标记 `Room.end_secs`**：房间进入终态时记录时刻，用于回收窗口计时。终态有两种来源：
  ① `closed = true`（队长解散 / 闲置过期）；② `phase = 2`（战斗结算完成）。
  结算入口统一走 `mark_settled(room, result)`，把「置 phase、置 result、记 end_secs」收在一处。
- **回收窗口 `RoomStore.reclaim_delay`**（默认 3600 秒，GM 用 `set_reclaim_delay` 调）：
  终态房间在窗口内仍可读取（客户端要看结算结果、掉落与履历），窗口过后才允许删除。
- **`reclaim_room(account, room_id)`**：**任何人**可触发，无特权（与 Keeper、过期同理）。
  断言 `(closed || phase == 2) && now >= end_secs + reclaim_delay`，否则 `E_NOT_RECLAIMABLE(30)`。
  通过后先释放房间内所有玩家成员的角色锁（`unlock_members`，**不记履历**），再
  `table::remove` 掉整条房间，发 `RoomReclaimed`。
  **房间号永不重用**（`Registry.next_room_id` 只增），因此回收不会让客户端缓存或
  `rng_seed` 派生规则错位。回收后房间相关视图一律 `E_ROOM_NOT_FOUND`。
- **关房即解锁**：`disband_room` 与 `expire_room`（大厅期）现在会调 `unlock_members`。
  此前成员角色保持 `room_id != 0`，只能靠自己再调一次 `leave_room` 才能解锁，
  而带着锁的角色进不了别的房间（`E_CHAR_IN_ROOM`）。关房语义上就该把人放出来。
- **战斗期停摆过期**：`expire_room` 从「只管大厅期」扩到**战斗期**。战斗中的房间若
  `now >= last_advance_secs + room_ttl`（默认 2 小时无人推进，例如 Keeper 长期停摆或全队弃房），
  任何人都能触发，按**既有超时规则**收尾（`settle_timeout`：扣救援费 + 记未通关履历 + 进入终态），
  事件 `RoomClosed{reason: 3}`。这里刻意复用 §6.3 已定案的「超时按全队被击败处理」，
  不新造「弃房免罚」的逃生口 —— 代价是 Keeper 长时间停摆会让在局队伍按超时结算，
  运营方需在此之前修复 Keeper 或调用 `emergency_advance`。
  已结算房间不再走 `expire_room`，直接等回收窗口。
- 新增视图 `room_reclaimable(room_id)`。事件 `RoomClosed` 的 `reason` 取值：
  1 = 队长解散，2 = 大厅闲置过期，3 = 战斗期停摆过期。

### 2.6.13 Move AP 机制实现口径（2026-09-30, 与 `gameplay-design.md` §4.6/§4.9 对齐）

§4.6 此前只写了「技能命中产出 AP」，没写引擎里那条每回合的自动产出，也没写计划为空时会被跳过。
本节把实现口径写全，作为 §4.6 的依据。

- **每回合自动产出**：`act_member` 在成员行动开始时先 `AP + 1 + ap_bonus`，封顶 `AP_CAP_BASE = 22`，
  再取计划里的下一个技能执行。这 1 点算进**本回合**可用余额（本回合就可能够放技能）。
  `ap_bonus` 来自资源词条「AP 产量 +1」，可叠加。
- **计划为空 → 整次行动跳过**：`act_member` 第一件事是读计划长度，为 0 就直接 return，
  连这 1 点都不给，也不推进计划指针。想攒点必须挂着一条非空计划。
- **被眩晕 → 整次行动跳过**：`act_all` 在调用 `act_member` 之前检查 STUN，命中则连那 1 点也不给。
- **技能产出发生在施放之后，与命中无关**：`resolve_skill` 在结算末尾把 `apGain` 加到成员 AP 上，
  这段代码在**多段循环之外**，所以每一段是命中还是落空都不影响产出。
  **与 §4.9 冲突**：§4.9 写的是「物理技命中后本可产出的 AP 也拿不到」，当前实现并非如此。
  是否改成「命中才产出」留给数值定案，本节按实现记录。
- **`apGain` 不受 `ap_bonus` 影响**：资源词条只加每回合那 1 点。
- **消耗与门槛**：`execute_skill` 用 `apply_ap_discount` 扣掉「AP 消耗 −1」词条后，若
  `member_ap < ap_cost` 立即失败，该回合什么都不做（计划指针已经推进，等同空过）。
  失败时**不扣 AP**（扣减发生在门槛检查之后）。敌人不走 AP 体系，`ap_cost` / `apGain` 对敌方技能无效。
- **跨战斗继承**：`spawn_battle` 只清空敌人与 `battle_turns`，不碰成员 AP，所以 AP 在整座地下城内连续累积。
- 新增视图 `member_ap(room_id, member_index)`：此前没有任何入口能读到成员 AP。
- 回归护栏：`test_ap_grants_per_turn_and_needs_a_plan`（计划为空不涨 AP）、
  `test_ap_gain_applies_even_when_the_cast_misses`（命中率压到下限后 AP 仍照常产出）。
  两条都验证过「撤掉实现即失败」。

### 2.6.14 Move 上线前修正（2026-09-30，可玩性 / 反滥用）

部署前审计发现「缺入口」与若干可被真实利用的漏洞。本节记录这一轮的定案与实现口径，
其中用户明确**允许保留**的三项在末尾单列。

- **随机数熵源改用 Aptos Randomness（AIP-41）**：此前 `room.rng_seed = room_id * 1000 + 1`，
  全部掷骰都是 `f(room_id, 行动序列)`，任何人都能离线算出整局结果。更糟的是
  `Registry.next_room_id()` 是公开视图、免费图开房零成本且不要求有角色，
  于是可以**零成本烧掉不吉利的房号**直到刷到对自己有利的一局。
  修复：所有消耗随机数的入口改为私有 `#[randomness] entry fun`，从
  `aptos_framework::randomness` 取协议随机数作为**该次交易**的熵。
  消费点：建号、开战、推进回合、兜底推进、进入下一场、命运骰子/重生卷轴。
  房内同回合的多次抽数仍走内部 xorshift 链（一次交易一次熵，链式保证同回合内抽数互不相同）。
  测试与仿真走 `#[test_only]` 的 `*_test` 变体，不注入协议熵，
  随机流与旧实现完全一致，**既有 162 个用例与全部标定值不变**。
- **玩家建号入口**（§2.1/§2.3）：此前只有 GM 的 `gm_mint`，玩家无法建号，游戏开不起来。
  新增 `character::create_character(account, class_id, skill_ids)`（`#[randomness]` 私有 entry）：
  玩家自定职业（`class_id = 0` 即无职业）与自选池技能（§2.6 流程，槽位外的截断），
  种族与词条随机掷出，不消耗任何资源。**首次建号额外发放启动资金 + 3 次免费重掷**（复用既有的 `created_before` 判定，
  按账号只发一次，防止「建号 → 卖号 → 再建」循环领取）。新增每账号角色数上限。
- **队长必须是在场队员**：`create_room` 不要求有角色，`start_combat` 只要求「有成员」且「调用者等于
  `room.leader`」，于是队长可以是完全不在队伍里的地址。而进入下一场（`advance_battle`）与推进回合
  只有队长能调，`ensure_leader` 又只在「退房/阵亡/逃离」触发 —— 队伍打赢第一场后会被**永久卡在间歇期**。
  修复：新增 `sync_leader(room, room_id)`，在 `start_combat` / `advance_turn` / `emergency_advance` /
  `advance_battle` / `disband_room` / `leader_retreat` 的入口先重算队长，
  队长恒等于「按加入序第一个在场玩家」（优先已到场者，其次存活未逃离者）。队长因此永远是队员。
- **推进权限独立成函数**：只有队长能常规推进（此前 `advance_turn` 是 `let _ = account;` 的裸入口，
  任何人都能把别人的房间按最快节奏推到回合上限并扣救援费）。判定集中在两处便于以后改策略：
  `can_advance(room, who)`（常规，队长）与 `can_emergency_advance(room, who)`（兜底，任何人，
  但要距上次推进 ≥ `EMERGENCY_SECS`）。兜底路径保留是为了队长掉线时房间仍能推进，
  它被 30 秒门槛限制成最多每 30 秒一次，不构成刷节奏的通道。
- **参与次数改为 24 小时滑动窗口**（§7.2）：不再用「挑战券兑出的额度」这种可无限堆积的账本，
  改为每账号保留**最近 N 次参与的时间戳**（N = 窗口上限，GM 可调），过期即丢弃，
  满则拒绝。**所有难度都计次，免费图也不例外**（免费图不再免额度，但仍是零入场费，
  负债者仍能进来打工复健，只是受同一个时间窗约束）。挑战券 / 每日挑战券两个道具及其
  入场额度机制、领取入口、掉落表条目一并移除。
- **全员逃离不计通关**（§6.2）：`leader_retreat` 此前 `release_all(room, true)`，
  于是「打到一半全员逃离」也能刷 `clears` 与 `best_difficulty`。现在记 `cleared = false`，
  并把房间结果从「1 = 胜利」中拆出来，单列 **3 = 全员逃离（提前收工）**。
  奖励照旧发放（§6.1），只是履历不认通关。
- **房间可被枚举**：链上 `Table` 不可遍历，客户端此前只能靠 indexer 扫事件。
  `RoomStore` 现在维护「活跃房间 id 列表 + id → 下标」索引，创建时追加、回收时 swap-remove，
  存储量与存活房间数同阶。新增分页视图 `active_room_count` / `active_room_at` 与 `room_exists`。
  已结算但未回收的房间仍在列表里（客户端可按 `closed` / `phase` 自行过滤，也便于有人来回收）。
- **变体抽选的两个缺陷（本轮的意外收获，影响内容生效）**：
  ① **权重不累加**：`spawn_battle` 的变体抽选循环里 `acc` 声明后再没被赋值，于是每轮比较的都是
  「0 + 当前变体权重」。两个变体的表（权重合计 1000）实际效果是「roll < 第一个权重 → 选第一个；
  否则**没有任何变体命中**，静默沿用这场战斗配置里的表」。后果：
  - **D9 战斗④ 70/30 变体从未生效**：配置表本身也是宝箱表，所以 30% 的「满编皇帝亲征」永远不出现，
    D9 末战事实上 100% 是砍宝箱；
  - **D5 战斗③ 20% 混沌变体从未生效**：非混沌分支回落到配置表（督军单挑），与 80% 基准同结果，
    所以肉眼与通关率都看不出来。
  修复：补上 `acc = new_acc;`。**这条 bug 靠「看结果」发现不了**（两条分支给出的可见结果相同），
  是写探针统计「实际抽到哪个变体」才暴露的 —— 新增回归用例
  `test_variant_selection_reaches_all_variants`（两个变体携带不同敌人数，断言两种都出现）。
  ② **`enemy_count` 挂在 `BattleConfig` 上**：变体只能换表、不能换敌人数，所以即便混沌变体生效，
  也只会出 1 只，与 §8.2「督军 + 魔像 + 哨兵混编」不符。修复：`VariantEntry` 增加 `enemy_count`
  （0 = 沿用本场配置），D5 战斗③ 的混沌变体设为 3；`add_battle_variant` 相应多一个参数。
  **连带标定**：混沌分支真正生效后 D5 solo 由 51/60 降到 48/60（80%，仍在 80-90% 带内）。
  混沌表原本是 750/180/70（三抽约 2.25 只督军），与世界观的「混编」不符且过难，
  已配平为 300/400/300（三抽约等于一督军一魔像一哨兵），这也让 D5 solo 回到 80%。
  `sim_late_ladder` 里 `w5 >= 12` 在 15 样本、真值 80% 下有约三分之一概率误报，阈值放宽到 10
  并注明「只用来抓明显掉出带外的回归」。**§2.6.8 的 51/60 ≈ 85% 是变体从未生效时测出来的，
  以本节数字为准。**

- **明确保留（用户定案，不修）**：
  ① **免费搭车**：中途加入的成员即使没参与过战斗也照常分奖池（入房不收费，`eligible_survivors`
  只看「在场」，不加参与度门槛）。
  ② **开战后不能踢人**：没有踢人/投票入口，恶意加入者只能靠他自己逃离离场。
  ③ **关卡内升级白花钱**：`upgrade_level` 不检查 `room_id`，而在房间里的属性是入房时快照的，
  所以关卡内升级对当前这局没影响。这是有意保留的误操作空间。

### 2.7.1 Move 道具层注记（数据驱动, 2026-09-02 实现）

- **每种道具 = item_type + ItemDef**（name/group/combat_usable/effect_kind/effect_value/decimals），**无 per-type struct**。
  GM 常驻 entry `item::register_item` 可**上线后动态添加新道具**（一笔交易, 零代码发布）。
- **fungible token 语义**：Vault 每 item_type 一张独立 address→u128 同质账本；decimals=18 约定
  `1 整份 = ONE = 10^18 raw`（平时按整份消耗, 允许拆散交易, `transfer` 支持任意 raw）。
- **战斗内使用** = 特殊技能 id `ITEM_SKILL_BASE(61440=0xF000) + item_type` 排进计划队列, **占 1 回合行动位**
  （§2.6 道具入队定案落地）；非战斗道具不可入队（`set_plan` 拒绝）；无库存/弹尽 → 空过不炸交易。
- **弹药**：620 左轮(铅弹×3)/630 龙击弹(×1), `execute_skill` 每次施放固定消耗（§2.5.2）；
  注册层 `reconstruct_skill_with_id` 已修复拷 ammo 字段（曾清零桩）。
- 初始道具: 铅弹/龙击弹(组1 弹药, 不可直接使用) + 魔素礼花(组2, 效果 kind=1 mana_boost +200)。

### 2.7 道具资产层：只用 ERC-20（带 Permit）与 ERC-721，不用 ERC-1155（用户定案）

> ⚠️ **本节为 EVM/Solidity 时代的资产层设计**（Conflux eSpace 语境）。当前 Aptos Move 实现不采用 ERC 标准，而是**自管同质账本 + GM 常驻注册入口**（数据驱动，上线后可动态添加道具）——**见 §2.7.1**。本节仅作设计意图与历史参考。

**标准选型**：道具分两类资产形态——消耗品/弹药是**同质化、可堆叠**资产 → 每类一个 **ERC-20 道具币**（`ItemFactory` 克隆部署，decimals=0 整数计数，模板内置 **ERC20Permit**）；角色与未来的「独特物品」（有独立身份/履历的稀有掉落）→ **ERC-721**。全系统**不使用 ERC-1155**——钱包、水龙头、市场等生态工具对 ERC-20/721 的支持最广。

**两层账本（approve 问题的结构性解法）**：道具余额有「游戏内」与「钱包」两种形态，边界清晰：
- **游戏内余额 = CombatEngine 内部账本**（`mapping(playerId => mapping(itemId => uint))`，与 AP/魔素同层的引擎 storage）。**游戏的全部循环都不碰 ERC-20**：地下城掉落直接记账、商店购买（扣 Economy 游戏币）直接记账、战斗消耗/弹尽判定直接读写计数器、**「给火枪手递子弹」= 引擎内部转账 `giveItem(队友, itemId, N)`（纯 SSTORE 挪动，~2 万 gas 一笔，无需对方任何操作）**——游戏内流转**零 approve、零 permit、零外部调用**。
- **钱包形态 = ERC-20 道具币**，仅在**外部交易**（场外 OTC、未来 DEX 挂单）时存在。出入边界两个函数：
  - `withdrawItem(itemId, N)`：内部余额 −N，引擎按 MINTER 角色 `mint` 给玩家钱包；
  - `depositWithPermit(itemId, N, deadline, v, r, s)`：玩家链下签 **EIP-2612 permit** 授权引擎，**一笔交易完成 approve + transferFrom + 入账**（引擎按 BURNER 角色 `burn` 销毁钱包币）——存回游戏**永远不需要单独的 approve 交易**；钱包里直接 `approve(MAX)` 一次性永久授权亦可（引擎是不可升级核心合约，风险面仅为道具本身）。
- 链上 ERC-20 `totalSupply` 恒等于「钱包流通量」，游戏内余额不出现在任何 ERC-20 里——账目天然清晰。

**approve 场景全表**（为何「反复 approve」不成立）：
| 场景 | 是否涉及 approve |
|------|----------------|
| 商店买道具（游戏币支付） | 否（Economy 内部账本） |
| 战斗用道具 / 引擎烧子弹 | 否（引擎内部账本） |
| 递弹药给队友 | 否（引擎内部转账） |
| 钱包 ↔ 场外交易（ERC-20 transfer） | 否（transfer 不需授权） |
| 从钱包存回游戏 | **permit 折叠进同一笔交易**（或一次 approve(MAX) 永久解决） |

**与 ERC-1155 方案的对比**：结算扣弹从跨合约调用（~30~50k gas）降为引擎内部 SSTORE（~5k）；ERC-20 的 transfer **没有接收回调**（重入面比 1155 的 `onERC1155Received` 更小，§6.0）；代价是道具类型多了要多部署克隆合约（~5 万 gas/类，一次性）。

## 3. 回合驱动服务（Keeper）

合约无法自己定时执行，必须由外部触发。两种结束模式对应：

- **自动回合**：一个 **Keeper 服务**（官方 Bot 与队长 CLI 均可担任，见 §1.5）监听区块/时间，达到「5 区块或 15 秒」即调用 `CombatEngine.advanceTurn()`。
- **手动回合**：任何玩家指令直接调用 `advanceTurn()`。

### 3.1 竞态与滥用防护（合约层强制）
- **`turnId` 单调推进 = 天然互斥**：同一房间的同一回合，只有**第一笔成功交易**能推进 `turnId`；并发的手动/自动交易中后来者在 `require(turnId == expected)` 上 revert（状态零变更，仅浪费调用者自己的 gas）。手动与自动无需区分处理，二者是同一个入口。
- **推进冷却**：每次推进记录 `lastAdvanceBlock`，`advanceTurn()` 要求距上次推进 ≥ 2 区块——任何人（包括恶意 CLI）都无法高频刷推进；冷却内的调用直接 revert。
- **手动推进不受「等满 5 区块」约束**：手动提前结束是玩法特性；推进后自动计时的基准重置，Keeper 重新等 5 区块。
- **Keeper 单点故障兜底**：合约不指定唯一 Keeper——**任何人**在「距上次推进 ≥ 30 区块」（远超正常回合窗口）后都可调用 `emergencyAdvance()` 推进回合（该函数只推进回合与超时判定，不含任何特权）。官方 Keeper 挂掉时，玩家的 CLI 或任何脚本都能解卡；正常节奏下 emergency 入口因 30 区块门槛而不可用。
- **超时判定随推进执行**：超时失败/房间过期检查内嵌在 `advanceTurn()` 中（推进时顺手检查），无需单独触发器。
- Keeper 同时也是 **预言机价格刷新**（§5）与 **超时/超回合失败判定** 的触发者。

## 4. 客户端：Discord / Telegram Bot 与自托管 CLI

### 4.1 身份映射（三种通道，一个 playerId）
- `chatUserId → playerId`（链上 uint/address 映射），首次聊天指令时由 Bot 注册。
- Bot 持有中继钱包，代 L1 玩家发交易并付 gas；聊天消息即「授权」。

- 合约层对三类通道一视同仁：都只是「某个 playerId 的指令」，只有「排技能只能排自己的」这类归属校验（§2.5）。


### 4.3 索引与展示
- Bot 跑一个轻量 **indexer**（监听合约事件），把 room/turn/combat 结果转成群内可读文本/表格，弥补链上只存权威状态、不存「好看」数据的短板。**弹药余量预警**：indexer 监听引擎内部账本事件与 SkillPlan——当火枪手弹药余额低于已排计划的剩余弹药总需求时，自动在频道播报预警（纯链下提示，不改链上状态）——「谁去给火枪手递几发子弹」成为群内协作信号。
- 队长 CLI 可开启**主播模式**接管本房间战报（同一事件流、同样的渲染模板），官方 Bot 检测到房间已有主播则自动让位，避免重复播报。

## 5. 菜市（TurnipMarket）与链上 DEX 中位价源（DexMedianPriceSource）

> 模型变更（用户定案）：旧版多空对赌（玩家互为对手方、池守恒、Oracle 4 小时刷新 + 批量结算）整体替换为 **10 倍杠杆永续差价合约、系统做对手方、盈利铸造/亏损销毁、价格即时读链上 DEX 流动性池、随时开平**——允许Char增发与操纵性暴富，安全边界从「零和结构」移到「中位数抗单池操纵 + 熔断预算封顶 + 不可转账锁死」。

### 5.1 价格源：链上 DEX 池中位数（零预言机、零推送、零受权地址）

```solidity
interface IPriceSource { function getPrice() external view returns (uint256); }

// Conflux eSpace 默认实现（可插拔适配器的首个实例）
contract DexMedianPriceSource is IPriceSource {
    address[] public pools;     // 治理注册的 CFX/稳定币流动性池（如 Swappi、Neko 等，选真实深度最好的 3~5 家）
    uint256  public minReserve; // 入选池最低流动性门槛（治理参数——剔除深度太差、几笔就能搬动的微型池）

    function getPrice() external view returns (uint256) {
        // 逐池 staticcall 读 getReserves() → spot = reserveStable / reserveCFX
        // 过滤 reserve < minReserve 的池 → 对合格报价排序取中位数（3~5 个元素，插入排序即可）
        // 合格池 < 2 时 revert（配置异常信号，宁可拒服不可用坏价）
    }
}
```

- **读取时机与方式**：`open` / `close` / `liquidate` 在结算时**即时读取**（纯 `view` 静态调用，每池约 2 千 gas，3~5 家合计约 1 万 gas）——**价格永远新鲜**，不存在「过期挂牌」与「只读模式」，也不需要任何受权推送地址（**推送式 PriceFeed 及其三条护栏——最小间隔/偏差带/新鲜度窗口——随推送模型一起整体退役**）。
- **中位数即护栏**：操纵菜价需**同时**把全部入选池的价格搬到同一方向——单池操纵（买爆一家）在取中位数时直接被其他池否决；要同时搬动多家池需要真实资本 + 承担全部滑点与往返损耗。操纵成本从「攻破一个推送密钥」变成「真金白银撼动真实市场」——**这是被用户定案承认并鼓励的明牌玩法**（巨鲸拉盘 CFX 后开看涨菜契收割，代价是真实市场的冲击成本，`gameplay-design.md` §7.3.1）。
- **配置护栏（治理注册，Timelock 8h）**：入选池由治理注册（增删池走配置类函数短锁）；`minReserve` 最低流动性门槛把「注册一个微型池然后单池操纵」堵在配置层；奇数个入选池使中位数无歧义（偶数取中间两均值，实现层支持但配置建议奇数）。
- **可插拔（与模块总线同思路）**：`IPriceSource` 是适配器接口，`TurnipMarket` 只依赖接口——其他链可换成 Chainlink 式预言机、WSTETH 锚定源或任何该链可用的公开价格；换价格源不触碰市场合约本体（不部署菜市则价格源也不部署）。
- **TWAP 为可选升级（非上线前提）**：现货价（spot）的经典补强是时间加权平均价（TWAP，Time-Weighted Average Price），但需要 checkpoint 历史存储与懒更新逻辑；本设计**默认不做**——操纵真实市场的成本已由中位数 + 敞口上限 + 熔断预算覆盖，且「瞬时插针被菜价照抄、恰好在场者暴富」本身是被承认的玩法。若未来数值层仿真认为插针套利过强，再以新适配器合约引入（换适配器不触碰 TurnipMarket）。

### 5.2 TurnipMarket：菜契的数据模型与结算
```solidity
struct Position {
    address owner;      // 归属 playerId 地址（无 transfer 路径，仓位不可转让）
    bool    isLong;     // 看涨/看跌
    uint96  margin;     // 押金（Char，托管在市场合约）
    uint64  entryPrice; // 开仓时读得的菜价（DEX 中位数）
    uint64  feeDebt;    // 持仓费欠账（惰性累计）
    uint40  openedAt;
}
// 杠杆为合约常量 LEVERAGE = 10；名义敞口 = margin × 10
```
- `open(isLong, margin)`：校验未熔断、单张名义 ≤ 上限、账号持仓数/名义合计 ≤ 上限 → **即时读 `IPriceSource.getPrice()` 记为开仓价** → 押金从 `Economy` 账本划入托管，收开仓手续费（销毁）。
- `close(positionId)`：再读一次当前菜价，计算 `PnL = margin × 10 × Δ%`（看跌取反）→ 连本带利划回（盈利部分铸造），亏损部分销毁；收收割手续费与欠账持仓费（销毁）。
- `liquidate(positionId)`：**无许可**。任何人可对「权益 ≤ 名义值 0.5%（维持保证金）」的菜契触发烂根（按即时菜价判定）：剩余权益 80% 归仓主、20% 归触发者（领赏激励 Keeper 化）。菜价由真实 DEX 池中位数构成，单次读价不可能被一笔交易操纵（需先搬动真实市场）；开仓与烂根判定之间的极窄穿仓区间由系统兜底铸造补零（合约层可审计的罕见事件）。
- **持仓费惰性入账**：`feeDebt` 只在任何触碰该仓的交易（open 不涉及、close/liquidate 必先补记）里物化——无全局循环、无人人皆付的定时交易。
- **每笔操作 O(1)**：对比旧版「刷新时批量结算全部头寸（O(头寸数) 循环 + settling 暂停标志）」，新模型每笔交易只碰自己的仓位——gas 更干净，也彻底消除了批量结算的 DoS 面。

### 5.3 熔断状态机（唯一净铸造阀门的总量闸门）
- 状态：`dailyEpoch`（`block.timestamp / 86400` 计日重置）、`dailyNetMint`（盈利支付计正、亏损销毁与费用销毁计负）、`circuitBreakerUntil`。**自然日重置而非滚动 24h 窗口**（用户定案的简化方向）：滚动窗口需要存储时间戳事件历史，自然日只需 piggyback 在任意一笔菜市交易上的「跨日则清零」检查（2 次 SLOAD/SSTORE），与打工/每日限额同款模式。代价是边界效应：午夜前爆量 + 午夜后新预算，最坏 24 小时跨度内最多放行 2× 预算——**预算数值按此最坏口径校准**即可（数值层 §11.1-7 仿真按自然日口径执行）。
- `dailyNetMint > 预算上限` → 置 `circuitBreakerUntil = now + 封市时长`（示例 12 小时）：期间 `open()` revert，**`close()`/`liquidate()` 照常**（玩家始终能离场，封市只封开新仓）。
- 预算按**全体账号合计**计——多账号（Sybil）无法稀释，这是取代旧版零和结构的规模化防线；预算数值与经济总盘子的比例由数值层定（§11.1-7 最坏情景仿真验收）。
- `TurnipMarket` 持有 `Economy` 的**受限铸/销角色**：铸造仅出现在 close/liquidate 的盈利支付路径，销毁仅出现在亏损与费用路径——链上恒等式 `净铸造 = Σ盈利支付 − Σ亏损销毁 − Σ费用销毁` 可被任何索引器审计，预算超限在合约层不可绕过。

### 5.4 RNG 与事件
- **菜市零随机数消耗**：全部结算由 DEX 中位菜价驱动，RNGRouter 不为菜市配置任何 Provider——「偶尔操纵随机数暴富」在本市场无落点；被承认的暴富来自真实市场操纵、瞬时插针与价差捕捉（`gameplay-design.md` §7.3.1 承认条款）。
- 事件：`PositionOpened` / `PositionClosed` / `PositionLiquidated` / `CircuitBreakerTripped`（每个仓位事件携带当次结算用的菜价快照，索引器可完整重放历史菜价）——indexer 播报群内（「菜价 1,024 烬/CFX，你的 3 号菜契烂根了」「菜市封市 12 小时」）。**无 `PricePosted` 类事件**——价格不是推送的，是结算时读取的；任意历史时刻的菜价可由「当时各池的储备快照」重放验证。
- **gas 预估**：open/close/liquidate 均 O(1)（约 5~8 万 gas 量级，含 3~5 池的静态读价与中位数计算）；**无任何推送交易**——旧版分钟级 `postPrice` 的日 gas 开销（约 0.6 亿/日）随推送模型一起归零，价格读取成本只发生在玩家自己的开平仓交易里。
- **重入面**：读价是对 DEX 池合约的纯 `view`（staticcall）调用——无状态写入、无回调执行，重入面为零（比旧版受权地址推送的外部调用面更小）。

> 对手方换成系统后，操纵菜价的收益上限从「对手方锁定金」变为「熔断预算内增发」：中位数抗单池操纵、敞口上限限宽、熔断限总量——操纵性暴富有硬上界且被官方承认（用户定案，操纵成本是真实市场的真金白银）；而暴富本身锁死在不可转账层（Char与菜契均无 transfer、余额不随角色 ERC-721 转移），最终经水槽回流销毁。安全模型是「预算闸门 + 结构性锁死」，不是密码学完美——这是有意的取舍。

### 5.5 Char娱乐模块总线（Ember Module Bus）：Char接入的通用协议（用户定案的扩展性要求）

> 动机：菜市证明了「Char + 独立娱乐模块」的形态成立（押金托管、结算铸造/销毁、预算熔断、不部署则游戏照常运转）。用户要求：**这套能力必须是通用的**——未来任何娱乐模块（竞猜厅、抽奖、竞技场、赛马、链主题特色玩法……）都能以同一种协议插入Char经济，而不需要为每个模块改造核心账本。菜市从「全系统唯一净铸造阀门」重新定位为「**总线上的首个铸销级模块**」。

**架构：Economy 内置模块注册表，而非逐模块授权**

```solidity
// Economy 合约内（核心账本自带接入协议，零额外合约）
struct ModuleGrant {
    uint8   tier;          // 0=禁用 1=托管级 2=铸销级（见下）
    uint32  minRakeBps;    // 托管级强制最低抽水（基点，结算分配时合约层强制扣除销毁）
    uint96  dailyBudget;   // 铸销级：自然日净铸造预算
    int256  dailyNetMint;  // 当日已用（piggyback 跨日清零，与打工/限额同款模式）
    uint96  totalMinted;   // 累计铸造（审计计数器）
    uint96  totalBurned;   // 累计销毁（审计计数器）
}
mapping(address module => ModuleGrant) public modules;
uint96 public globalDailyBudget;   // 全局合计净铸造预算（全部铸销级模块之和的上限）
int256 public globalDailyNetMint;  // 当日全局合计（超限 → 全体铸销级模块联动封市）
```

**两级权限（按「模块是否铸造Char」划线）**：

1. **托管级（tier 1，escrow-only）**：可调用 `escrow(player, amount)`（玩家Char划入该模块托管）与 `settle(players[], amounts[])`（结算分配——托管池按玩法结果分回多个玩家）。**零铸造权限，净铸造恒为零**。适用「玩家对玩家」型玩法（竞猜对赌池、PvP 竞技场报名与奖金）。
   - **反转账红线（关键安全约束）**：托管池的资金**只能回到玩家或被销毁**，且任何 `settle` 分配被**强制扣除 `minRakeBps` 抽水销毁**（注册时治理设定，模块不可自降）。原因：若无抽水，托管级模块可被用作**变相 P2P 转账通道**（A 与同伙对赌 1:1 转移Char）——击穿「Char不可转账」这道最硬的女巫防线（`gameplay-design.md` §7.6 三道通用防线之首）。抽水使 1:1 转移必然磨损，转账套利结构性亏损。
2. **铸销级（tier 2，mint/burn）**：托管级全部权限 + `mintTo(player, amount)` / `burnOf(player, amount)`。适用「系统做对手方」型玩法（菜市即此级；未来的竞猜厅若做系统赔率支付、抽奖房、赛马庄家……）。**每次 mint 走双预算闸门**：该模块 `dailyNetMint` 超其 `dailyBudget` → 本模块熔断；全局 `globalDailyNetMint` 超 `globalDailyBudget` → **全体铸销级模块联动熔断**（各自禁止开新仓/新下注，存量结算照常——「玩家始终能离场」原则全总线通用）。

**预算模型与菜市同构**：双闸门均用**事后计量 + 自然日重置**（`block.timestamp / 86400`，与菜市熔断/打工/每日限额完全同款模式），不搞预扣预留——实现最省（每笔 mint 两次 SLOAD + 一次 SSTORE/累加），代价是熔断触发笔与午夜边界最坏放行 2× 预算，**全部预算数值按最坏口径校准**（§11.1-7 既有口径直接推广）。**菜市自身的模块内熔断保留**（封市 12 小时、只封开仓——比 Economy 层的日预算闸更细的行为语义）；Economy 层双闸是跨模块的最后防线，正常情况下永远不触发（模块自己的预算 ≤ 总线配额）。

**接入流程（治理白名单，非无许可）**：新模块 = 独立合约部署 → TimelockController 短锁注册（与配置类函数同通道，§6.2——8 小时锁，社区可提前审查模块代码与预算申请）→ 设定 tier、minRakeBps（托管级）、dailyBudget（铸销级）。可随时撤销（tier 置 0，存量托管按该模块自身的退出结算流程清退——注册时即要求模块实现 `onRevoke()` 全员退款入口）。**Char核心账本本身不升级**：注册表是 Economy 的初始字段集，上线第一天就存在（首条记录 = TurnipMarket），此后加模块只是写新槽位。

**审计口径（逐模块可审计恒等式）**：`模块净铸造 = totalMinted − totalBurned`（per-module 计数器 + `ModuleMint/ModuleBurn/ModuleBudgetTripped` 事件）——菜市现有恒等式「净铸造 = Σ盈利支付 − Σ亏损销毁 − Σ费用销毁」推广为每个模块一条，索引器可对总线出**分模块通胀报表**；`globalDailyNetMint` 是全体铸销级模块的合计日通胀率读数，运营监控直接读链。

**现有模块迁移成本**：TurnipMarket **零改动**——它已按 RBAC 持角色，注册表只是把「单例角色授予」换成「白名单槽位之一」；其模块内熔断/敞口上限照旧（价格护栏已改为 DEX 中位数，§5.1）。商店（Shop）**不走上总线**：商店是纯销毁水槽（Char单向流出换弱消耗品），不是娱乐模块，继续走普通扣费路径。

**gas 影响评估**：零额外负担——注册表只在模块 mint/escrow 路径上多一次 mapping SLOAD 与累加（模块本就要写自己的状态），对玩家日常动作（战斗/升级/入场）**零边际**；未注册任何 tier 2 模块时（如「不部署菜市」的极简链配置），全局闸恒为零放行，总线完全沉默。

**首版部署范围**：仅注册 TurnipMarket 一个模块（tier 2）。总线协议的其余部分（注册函数、托管级 settle、全局闸）随 Economy 一次部署到位但无消费者——**保留可能性，不预付复杂度**：未来模块上线时零核心改动，纯新增。

## 6. 安全与风控

### 6.0 重入防线（道具/弹药场景专项）
- **战斗消耗路径零外部调用**：弹药/道具扣减全部在引擎**内部账本**（§2.7）——结算调用链上没有任何外部合约交互，不存在受攻击者控制的代码执行点。
- **递弹药路径无回调面**：`giveItem` 是引擎内部转账（纯 SSTORE）；唯一涉及外部代币的 `depositWithPermit` / `withdrawItem` 走标准 ERC-20 **transferFrom / mint——ERC-20 没有接收回调**（对比 ERC-1155 的 `onERC1155Received`，重入面天然更小）。
- **纵深防御**：CombatEngine 所有状态变更外部函数统一加 `nonReentrant` 守卫 + 遵循 CEI（先检查、后效果、最后交互）顺序——即使未来引入带回调的外部交互（如第三方支付代币），回调重入也只会撞上守卫 revert。
- **角色在房间内时 transfer 被 CharacterRegistry revert**（§2.1）——合约钱包也无法通过「战斗中转移角色」破坏弹药归属一致性。

### 6.1 中继器（Bot）权限模型
- Bot 代发的每笔交易**必须来自该玩家的明确聊天指令**，指令原文哈希随交易上链（审计可回溯）；Bot 无自有游戏操作权限。
- **速率限制**：每 playerId 每分钟动作数上限（合约层 `Limits` 同步校验，双保险）。
- **防冒充**：严格绑定 chatUserId → playerId；绑定变更需双通道确认（旧通道 + 新通道各一次）。
- **Bot 无排他性**：任何房间任何人可随时切到 CLI 通道自付直发；Bot 作恶的影响被「指令可审计 + 通道可切换 + 链上状态权威」三重限制。

### 6.2 治理与可升级性
- **资产不可升级**：角色 NFT、道具 ERC-20 币与工厂、`Economy` 账本为不可升级合约（只加不可变逻辑），所有权数据永不被升级逻辑触碰。
- **逻辑可升级**：`CombatEngine`、`SkillRegistry`、`TurnipMarket`、`DexMedianPriceSource` 等用可升级代理；升级权限归**多签（如 3/5）+ 48 小时时间锁**，时间锁内升级计划公示于链上事件，玩家可审计甚至提前撤离资产。
- **紧急暂停**：多签可全局暂停（Pausable）——用于漏洞应急；暂停期间战斗冻结但资产安全，恢复需再次多签。
- **配置类函数**（难度参数、税率、限额、RNG Provider）单独走 **TimelockController 短时间锁（如 8 小时）**，改配置无法突袭。

### 6.3 全局硬上限与限额（合约常量/可调参数上限）

| 项 | 上限 | 目的 |
|----|------|------|
| 单房间同时在场单位 | 角色 ≤10 + 敌人 ≤10 | 结算 gas 有界 |
| 技能 effects 数 | `Effect[4]` 固定数组 | 类型层防 DoS |
| 前瞻计划长度 | 16（`uint16[16]` 固定） | 存储/gas 有界 |
| `SkillRegistry` 注册总数 | ≤1024 | 防垃圾注册 |
| 同时存活房间数 | ≤1000 | 状态膨胀控制 + 房间过期回收 |
| 单回合事件数 | ≤64（超出合并为摘要事件） | 索引器/战报可用性 |
| 菜价源 | 治理注册 3~5 个 DEX 池 + `minReserve` 门槛 + 中位数（池增删走 8h Timelock） | 单池操纵被中位数否决；微型池被流动性门槛剔除 |
| 菜契敞口 | 单张名义 ≤5 万Char；每账号 ≤5 张、名义合计 ≤10 万Char | 限制单账号暴富上限与状态膨胀 |
| 菜市净铸造 | **自然日**预算封顶 + 超限封市（仅可平仓） | 经济不崩溃的总量闸门，多账号稀释无效 |

| GM 测试权限 | `gmEnabled` immutable（测试网 true / 主网 false）+ 角色零授予验收断言 | 主网物理移除任意铸造后门（§6.7） |

### 6.4 开放链上经济的安全边界（防 Sybil / 防信息滥用 / 防税基绕过）

游戏跑在开放区块链上，必须承认三个**不可防御事实**，并把强制力只放在**合约入口**：

1. **无限账号（Sybil 不可防）**：无 KYC（Know Your Customer，实名认证）的开链环境里，工作室可开无限多账号。一切按账号的限额（入场次数/购币/开仓/打工）都是**软约束**，会被多号稀释。硬防线有三条：
   - **gas 经济压制**：每次链上动作都有真实 CFX 成本。CLI 自付通道天然如此；设计上保证**单账号单动作的期望可变现产出 < 其 gas 成本**（打工奖励校准低于打工 gas；道具掉落与强度使刷号的期望收益低于规模化 gas 开销）。
   - **Bot 通道配额封顶补贴**：官方代付的 L1 通道按账号设每日动作配额——补贴总量的上限 = 配额 × 账号数，配额收紧即可控；Bot 对异常模式（同 IP 段、同节奏批量操作）可做链下风控（Bot 是中心化服务，这是它的天然权利与义务）。
   - **可转移资产价值有天花板**：道具强度上限 + 极品角色被「重掷道具商店价」套利锚定（§7.4）——工作室能刷出的东西单件价值有限，规模化利润空间被封顶。
2. **信息不可屏蔽**：链上状态任何人可读。**词条、仓位、敌人配置、掉落率、技能循环全部公开**——设计不依赖任何「隐藏」机制（无售前隐藏、无盲盒依赖）；博弈全部按公开信息设计（菜契仓位公开可查、历史菜价可由各池储备快照重放、技能循环可查）。
3. **转移环节半可强制**：链上改变资产 owner 的**唯一途径**是官方 NFT/ERC-20 合约的 transfer 系函数（approve 只是授权、不转移所有权，无旁路）——因此**与价格无关的转移规则（等级重置、固定费、冷却）可在 NFT transfer / ERC-20 的 `_update` 钩子内 100% 强制**（角色等级重置即用此法，`gameplay-design.md` §7.4）。不可强制的只有**按成交价百分比抽税**（成交价与支付可完全留在链下），经济模型对此零依赖。道具当前保持零转移限制，需要时可在 ERC-20 的 `_update` 钩子随时加规则。
4. **游戏币与大头菜账本是强强制层**（对我方有利）：二者均非代币，是合约内部 mapping，无 transfer 接口、无场外交易可能（无法把 mapping 条目交给别人；托管账号共享等于交出全部资产）。主水龙头（打工/通关收益）全部沉淀在这一层，通胀锁死在不可转账层内；美元购买只走官方商城单向入金。

**GasTreasury 的诚实定位与付费回收模型**：中继 Bot 的 CFX 成本回收**主力是 L1b 充值计费**（玩家直接付 CFX/美元，覆盖 gas + 服务费，见 §1.5 三层通道表），而非游戏币动作费。动作费（游戏币）的真实作用是**链上层的防刷摩擦与速率限制第二道闸**（对 Bot 通道和直连通道一视同仁），**不构成 CFX 回补闭环**（游戏币没有链下变现通道）。L1a 免费配额是获客支出，被配额硬性封顶；补贴总量的现实控制 = L1a 配额 × 账号数 + Bot 链下风控 + 持续引导用户向 L1b/L2 迁移。

### 6.5 CLI 播报防伪造
- CLI 发往聊天频道的**声明类消息**（「我排了技能」）必须附带：动作的**链上交易哈希**（已确认上链）或**钱包对消息的签名**；频道侧渲染组件校验签名/哈希，未验证消息显示为「未验证发言」，与链上权威战报视觉区分。
- **战报主播模式**播报的每条战报都源自链上事件（附 tx hash），主播无法编造战斗结果——最多美化措辞。

### 6.6 随机数
按用途可插拔配置（§2.3），默认游戏级区块熵；对抗「重掷刷词条」依靠经济手段（重建消耗道具、每日创建/入场上限、动作费、频控），不依赖密码学强度。

### 6.7 Game Master（GM，游戏管理员）权限：测试网全功能、主网可物理移除（用户定案）

> 需求：测试阶段需要多人持有的 GM 权限，能**任意制造道具、角色和游戏币**（搭建测试场景、复现 bug、发放测试资产）；主网上线时**允许彻底不保留**这种权限——不是「承诺不授予」，而是**功能在主网上物理不存在**。

**设计核心：一个 immutable 总开关 + 三处 GM 入口 + 全事件可审计**

```solidity
// 各核心合约共用模式（以 Economy 为例）
contract Economy is AccessControl {
    bytes32 public constant GAME_MASTER_ROLE = keccak256("GAME_MASTER_ROLE");
    bool public immutable gmEnabled;   // 构造参数：测试网 true / 主网 false——不可变，部署后无法再开

    constructor(bool _gmEnabled, ...) { gmEnabled = _gmEnabled; ... }

    modifier onlyGM() {
        require(gmEnabled, "GM_DISABLED");               // 主网：无论谁持角色都 revert（物理移除）
        require(hasRole(GAME_MASTER_ROLE, msg.sender), "NOT_GM");
        _;
    }

    function gmMint(address to, uint96 amount) external onlyGM { ... emit GmMint(to, amount, msg.sender); }
    function gmBurn(address who, uint96 amount) external onlyGM { ... }   // 修正测试数据（账本支持负数，修负余额同路）
}
```

**三处 GM 入口（覆盖三类资产的任意制造）**：

| 合约 | GM 入口 | 说明 |
|------|---------|------|
| `Economy` | `gmMint(who, amount)` / `gmBurn(who, amount)` | 任意Char铸造/销毁（含直接修复负余额——账本本就支持负数） |
| `CombatEngine` | `gmGiveItem(playerId, itemId, count)` | 任意道具**直写金库内部账本**（零 ERC 调用，测试玩家立即可用）；需要钱包形态时 GM 经引擎既有 MINTER 角色走 `withdrawItem` 等价路径 |
| `CharacterRegistry` | `gmMintCharacter(to, classId, race, affixIds[], skillIds[])` / `gmMintCharacterAtLevel(to, classId, race, affixIds[], skillIds[], level)` | **指定全属性**的角色创建：种族、职业、词条、自选技全部显式指定——**绕过 RNG（不走 AFFIX 随机源）、绕过创建费、绕过每日创建限额与首角色判定**。测试「硬精品构筑」不再需要掷几万次；`AtLevel` 变体额外显式指定**等级**（≤`MAX_LEVEL=300`，能力值按 `满级基准 × level / 300` 线性回插）——用于直达满级测试（例如 300 级、无加成 HP = 3 万，`content-design.md` §8.2 / `gameplay-design.md` §2.4），也用于测试角色/词条在不同等级下的成长曲线 |

**多人持有**：`GAME_MASTER_ROLE` 是标准 RBAC 角色，`grantRole`/`revokeRole` 可授予任意多地址（测试团队每人一个，或再套一层 GM 多签）；授予/撤销走治理 Timelock（与配置类函数同通道，§6.2）——测试网也建议走短锁，留下授权审计痕迹。

**主网移除的三层保障（层层递进，最终是物理的）**：
1. **部署期决定（最硬）**：`gmEnabled` 是 **immutable 构造参数**——主网部署脚本传 `false`，此后 GM 入口**永远 revert**，连治理多签 + 时间锁都开不了（对比：若用 mutable 开关，「未来某天被治理重新打开」的后门永远存在，与「不保留」语义不符）。核心合约不可升级（§6.2），意味着这扇门焊死后无法再开。
2. **角色零授予（部署验收项）**：主网部署清单断言 `getRoleMemberCount(GAME_MASTER_ROLE) == 0`——即使 `gmEnabled` 误配为 true，无人持角色同样不可用；上线验收脚本必须包含此断言（与「资产合约不可升级」同列为主网硬验收项）。
3. **链上可验证**：`gmEnabled` 与角色授予列表都是公开链上状态——任何人（玩家、审计方、交易所上架审核）可直接读合约验证「主网无 GM 后门」，无需信任官方声明。

**审计与信任设计**：
- **全部 GM 操作发事件**（`GmMint` / `GmItemGranted` / `GmCharacterMinted`，携带操作者地址）——测试网公开 GM 日志反而增强信任：测试资产的来源全部可追溯，社区能区分「测试资产」与「正常玩法产出」；索引器可出 GM 操作报表。
- **GM 入口与正常入口同一条状态写入路径**（`gmMint` 调用内部与打工收益同一个 `_credit` 函数、`gmMintCharacter` 复用角色创建的状态写入）——GM 制造的资产与正常资产**状态结构完全一致**（测试真实性），仅来源事件不同。
- **GM 不 bypass 安全红线**：GM 入口只增发资产，**不触碰战斗结算逻辑**（战报依然只由引擎状态机产生）、不修改他人角色属性（修正构筑用 `gmMintCharacter` 造新号，不改存量——避免「GM 改属性」这类无法审计的隐性变更）。
- **GM 权限 ≠ 治理权限**：GM 是测试工具（资产制造），治理是运营权限（参数/升级/暂停，§6.2）——两者角色分离；主网移除 GM 不影响治理（治理在主网必须保留，GM 不必）。

**跨网络隔离（无需设计）**：测试网与主网是不同网络上的不同合约实例——GM 造的测试角色/道具/Char天然不会流入主网（ERC-721/ERC-20 的 tokenId 在另一条链上无对应物），无需任何标记位或隔离机制。

**与 §6.4 / gameplay §7.6 的关系**：GM 入口是**测试网专属的铸造口**，出现在 `gameplay-design.md` §7.6 女巫攻击审查表中作为唯一一行「主网不存在」的条目——主网上线时该入口被上述三层保障物理移除，经济模型的「净铸造阀门仅模块总线」结论（§5.5/§7.5 判据①）在主网严格成立。

## 8. 关键结论速览
1. **链选型：Conflux eSpace（纯 EVM 兼容）**，不用 Core Space。
2. **代付 gas 分层解**：L1a Bot 免费配额（获客支出封顶）、L1b Bot 充值计费（CFX/美元，gas 由用户付——商业主回收通道）、L2 自托管 CLI 自付、L3 钱包直发——付费墙在 Bot 通道层，合约保持无许可。
3. **技能引擎「数据多、原语少」**：`Skill`/`Effect[4]`/`MonsterAI` 全数据化，目标选择全随机（RNG 驱动），最坏回合结算 gas 有硬上限。
4. **技能计划是链上状态**（`uint16[16]` 环形队列），不是聊天口述；只能给自己排。
5. **经济三闸门（开放链上版）**：游戏币不可转移主账本（唯一强强制层）、可转移资产价值天花板（道具强度上限 + 重掷套利锚）、gas 成本对动作的经济压制（Sybil 硬防线）——不依赖限额、隐藏或转移税这些做不到的事。
6. **失败惩罚经济化且不可滥用**：固定救援费（难度挂钩，阶梯计数已删——期望不等式按次成立，阶梯冗余）、负余额无上限但限制行为且收益优先偿债、欠债仍可免费游玩与打工（无死局）；工作室威慑靠 gas 经济而非救援费。
7. **治理防突袭**：资产不可升级、逻辑升级走多签+48h 时间锁、配置 8h 时间锁。
8. **需外部服务**：回合驱动 Keeper 与价格预言机都依赖链下触发，无法纯链上自驱；emergencyAdvance 提供任何人可用的解卡兜底。
