# 摸哈游（Mohayo）：技术实现设计

> 配套文档：`gameplay-design.md`
> 核心问题聚焦：**链选型、Conflux Core Space 代付 gas 是否必要、Discord/Telegram 用户能否自己付 gas、以及整体合约与客户端架构**。

---

## 1. 链选型与 Gas 支付问题（核心决策）

### 1.1 Discord / Telegram 用户能否自己付 gas？——结论：原生场景下「很难」

把区块链当后端、把聊天软件当客户端，会撞上一个结构性矛盾：

1. **聊天用户默认没有钱包**。Discord / Telegram 账号 ≠ 区块链地址。要让用户「自己付 gas」，前提是他得先有一个持有 CFX（或任何原生币）的钱包——这直接劝退 99% 的聊天用户。
2. **钱包审批会打断聊天流**。即使接入钱包，「在群里发一句指令 → 弹出钱包签名 → 等待上链」的体验，与「在群里聊天即游戏」的初衷相悖。
3. **原生 CFX 获取门槛**。即便有钱包，还要先买 CFX，对纯聊天玩家是额外负担。

所以：**在「纯聊天客户端」前提下，指望用户用自己的钱包原生支付 gas，UX 不成立。** 这不是 Conflux 特有的问题，所有 EVM 链都一样。

### 1.2 「代付 gas」的几种方案对比

| 方案 | 机制 | 用户是否付 gas | 是否需要 Core Space | 评价 |
|------|------|----------------|---------------------|------|
| A. 用户原生自付 | 用户钱包直接发交易 | 是（CFX） | 否 | UX 差，需钱包，不适合聊天场景 |
| B. Conflux Core Space 代付 | Core Space 原生 sponsor 机制，白名单内调用由赞助者付 gas | 否（赞助者付） | **是** | 用户仍需 Core Space 钱包并签名；且 Core Space 非纯 EVM（地址/账户模型不同） |
| C. 中继器 + 元交易（Relayer / Meta-Tx） | 玩家用聊天身份授权，Bot 用自己的钱包代为发交易并付 gas | 否（中继者付 CFX） | 否 | **用户零钱包摩擦**；中继成本按通道分级回收（L1a 免费配额封顶补贴 / L1b 充值付费，§1.5），不依赖游戏币回补 |
| D. 托管账户（Custodial） | Bot 掌握玩家账户私钥，代玩家发交易 | 否（运营付） | 否 | 最顺滑，但中心化托管，需明确信任模型 |

### 1.3 是否需要 Conflux Core Space 代付？——**结论：不必要，不建议**

- 你的硬性偏好是「纯 EVM」。**Conflux Core Space 并不是 EVM 等价**（它使用自己的账户/地址格式与存储模型），而 **Conflux eSpace 是完整 EVM 兼容**。选型应优先 eSpace，以契合「纯 EVM 链」目标。
- Core Space 的代付本质是「赞助者付 gas + 用户仍需 Core 钱包签名」。相比而言，**方案 C（中继器 + 元交易）在 eSpace 上能做到用户连钱包都不需要**，体验更好，且不锁定到 Core Space。
- 因此：**我不认为 Core Space 代付 gas 是「非常必要」的**。用 **eSpace + 中继器** 即可覆盖代付需求，且更灵活（回补逻辑写在你自己的合约里）。

### 1.4 推荐架构：eSpace + 中继器 + 游戏币回收（解决「不想一直补贴」）

为了同时满足「聊天体验顺滑」和「不想永久补贴 gas」，采用 **方案 C 的演进版**：

```
玩家(Discord/TG) ──聊天指令──> Bot(中继器/信任锚)
                                      │ 用 Bot 自己的钱包发交易
                                      ▼
                              Conflux eSpace 合约  ←── 预言机/Keeper 也走这里
```

- **玩家不持钥匙**：聊天身份（Discord user id / TG user id）映射到链上 `playerId`，授权由「聊天身份」担保，Bot 是信任锚与代签者。
- **Bot 付 CFX gas，且不是永久白贴——按通道分级回收**（详见 §1.5 三层通道表与 §6.4）：
  - **L1a 免费档**：每账号每日小额免费动作配额，是获客支出，**总量被配额硬性封顶**；
  - **L1b 充值档**：玩家向官方充值 CFX/美元，按动作计费（gas × (1+服务费率)）——**gas 成本回收的主力通道**；
  - 游戏内对每类动作收取的**游戏币动作费**只是链上层的**防刷摩擦与速率限制**（进 GasTreasury 销毁），**不构成 CFX 回补闭环**；
  - 效果：**重度聊天用户要么付费（L1b）、要么迁移 CLI 自付（L2），免费补贴只覆盖轻度新用户**——保住聊天 UX 的同时避免无限补贴。

### 1.5 方案 E：自托管 CLI 客户端（用户真正「自主支付 gas」的路径）

补充一条重要方案：官方提供**开源命令行程序（CLI，Command-Line Interface，命令行界面）**，玩家在自己的电脑上运行：

- **私钥本地持有**：玩家在 CLI 中导入自己的 eSpace 私钥（本地加密保存或环境变量引用），私钥**永不离开本机**。
- **直连链上、自付 gas**：CLI 通过公共 RPC（Remote Procedure Call，远程过程调用）节点直接发送交易——排技能、加入房间、逃离、买入大头菜等全部动作由玩家自己的钱包签名并支付 gas。**没有任何中继，没有托管**。
- **回写聊天频道**：CLI 同时作为一个轻量聊天机器人，把玩家自己的动作（「我安排了下回合用斩铁剑」）**发送到指定的 Discord 频道或 Telegram 群**——群友无论用哪种客户端，看到的信息流是一致的。
- **队长主播模式**：队长的 CLI 额外承担**战报主播**职责——监听链上事件流，把整场战斗过程渲染成文字实况发到群里。也就是说，「解说」不需要官方 Bot 也能存在，任何玩家都可以为自己的房间提供解说。
- **Keeper 模式**：CLI 可选开启 Keeper 循环——当「5 区块 / 15 秒」到期而无人手动结束时，由该 CLI（通常是队长的）自动调用 `advanceTurn()` 并支付该笔小额 gas。一个全员使用 CLI 的房间**不依赖任何官方基础设施**即可完整运转。
- **身份统一**：钱包地址与聊天账号绑定到同一个 `playerId`（绑定流程：Bot 下发一次性验证码，CLI 用钱包私钥对验证码签名回传验证）。同一 `playerId` 可随时混用「群聊指令（Bot 代发）」与「CLI 直发」两种通道。

#### 三层客户端并存架构（最终形态）

| 层 | 通道 | gas 谁付 | 费用模型 |
|----|------|----------|----------|
| L1a 纯聊天·免费档 | Discord / TG 群里发指令，官方 Bot 代发交易 | Bot 垫付 | **每日免费动作配额**（很小，官方随时可调；超出即拒绝代发）——获客成本，运营支出封顶 |
| L1b 纯聊天·充值档 | 同上，但玩家已向官方充值 CFX 或美元 | Bot 垫付（由充值覆盖） | **按动作计费**：单价 = 实测 gas × (1 + 服务费率)，公开价目表；Bot 链下账户余额扣减，余额不足拒绝代发 |
| L2 自托管 CLI | 本机 CLI + 自己的私钥 | **玩家自付 CFX** | 无任何平台费用，无配额 |
| L3 纯链上 | 任何钱包/脚本直接调合约 | 玩家自付 | 无（合约无许可，永远开放） |

**付费墙的合法性边界**：限制发生在 **Bot 通道层**（中心化服务，天然有权决定服务谁、收多少），不是链上层——游戏合约保持无许可，L2/L3 玩家不受任何影响。不付费玩家「被限制游玩次数」的具体形态就是 L1a 免费配额用尽后 Bot 停止代发；想继续玩有两条路：充值（L1b）或 CLI 自付（L2）。这直接满足商业目标：**官方对 L1a 的补贴被配额硬性封顶，L1b 用户的 gas 由自己支付，L2/L3 零补贴**。

官方 Bot 在此架构下退化为「L1 的代发器（含计费）+ 全局 Keeper 兜底 + 价格预言机」，而不再是游戏的必要组件——**游戏的核心运行只依赖链，不依赖官方服务器**，这与「纯区块链后端」的定位自洽。商业上，L1a 免费配额是获客漏斗，CLI 体验优化（一键安装、战报美化）持续引导用户向 L2 迁移。

#### 私钥安全要求
- CLI 不得以明文存储私钥：使用 keystore 文件 + 口令加密，或环境变量引用。
- 建议支持硬件钱包签名（Ledger 等 EVM 标准设备），CLI 只构造交易不接触私钥。
- 验证码绑定流程中，验证码必须由**钱包签名**而非私钥明文传输；验证码一次性、短时效。

## 2. 智能合约架构（Solidity / eSpace）

### 2.1 合约清单与职责
| 合约 | 职责 |
|------|------|
| `CharacterRegistry` | 角色 CRUD、职业/**种族**/词条/等级/**履历**/属性计算（**种族修正各属性上限**：`min(种族上限表, 基础公式)`，种族技能在创建时并入技能列表；**种族创建时随机生成、永久不可改**；**词条模板注册**：方向（正面/双刃/负面）× 档位（1~5 级长尾）的数值分布由模板数据承载，创建时经 RNG 依次掷「方向 → 词条 → 档位」，负面词条不可单洗、只能整体重掷，`content-design.md` §6）、公共池自选技锁定（**人类种族 +2 个自选槽**）、等级硬上限；角色 ERC-721 的 **transfer 函数内直接执行等级重置**（所有权变更必经之路，`gameplay-design.md` §7.4）；**角色在房间内（未结算离场）时 transfer 直接 revert**——战斗中角色所有权不可变更（保护弹药归属、技能计划与战斗状态的一致性，离场/结算后自动解锁） |
| `RoomManager` | 房间/关卡生命周期、难度绑定、入场费（销毁）/免费标记、人数上限、队长权限、加入序号（`joinSeq`，供队长按加入顺序自动继任）、加入/逃离、房间过期 |
| `CombatEngine` | 地下城/战斗、回合、行动顺序、随机目标结算（含权重模式）、技能结算、**房间级魔素池（跨战斗继承）**、AP、召唤与动态加入、道具经技能队列使用（**占行动位、不限次数**）、收益随机分配（RNG 权重）、**道具金库内部账本**（§2.7：存入/取出/内部转账/战斗消耗都在引擎 storage 里，零 ERC 调用） |
| `SkillRegistry` | 职业技 + 公共池技能的数据化定义（`Skill` 结构，见 §2.5，可扩展；注册总数有硬上限） |
| `ItemFactory` | 道具币工厂：每类消耗品/弹药部署一个 **ERC-20 道具币**（EIP-1167 最小代理克隆，~5 万 gas/类；decimals=0 整数计数；模板含 **ERC20Permit**，EIP-2612）——**全系统不用 ERC-1155**（用户定案，§2.7） |
| `Economy` | 游戏币内部账本（**支持无上限负数**、禁止 P2P 转账）、升级/商店/入场费扣费、负债行为限制、阶梯救援费、**打工**（每日一次，奖励校准低于 gas 成本） |
| `Market` | 大头菜多空对赌市场：封闭资金池、按预言机锚定价结算、失衡费、点差销毁、每日限额，依赖 `IOracle` |
| `Oracle` | CFX 价格来源（见 §5；受权更新 + 最小刷新间隔 + 延迟生效） |
| `GasTreasury` | 游戏币动作费的收集与销毁（防刷摩擦 + 链上速率限制闸；**非 CFX 回补闭环**，见 §6.4） |
| `RNGRouter` | 可插拔随机数路由：按用途配置来源（见 §2.3）；随机目标也经此路由 |
| `Limits` | 集中式限额库：每日入场/购币/开仓限额、挑战券豁免、打工每日一次（`day = block.timestamp / 86400`，映射 `keccak256(playerId, day) => count`；**软约束**——多账号可稀释，硬防线见 §6.4） |

### 2.2 状态建模与 gas 成本
- **最小化链上状态**：房间/角色/怪物 HP/魔素/技能计划属于「权威必须上链」的状态，放在合约 storage。
- **展示层走事件 + 索引器**：Bot 订阅合约事件，在群内渲染可读战报，避免每次查询全量链上读。
- **storage 优化**：角色属性可存为 `uint` 打包或 `struct`；技能计划用紧凑数组；房间数量设上限以控成本。
- **游戏币用内部账本而非 ERC-20**：因为禁止 P2P 转账且需支持负数，内部 `mapping(playerId => int256)` 最简单。

### 2.3 随机数（RNG）：可插拔、可配置、游戏级优先

#### 2.3.1 立场：游戏级随机数 + 来源必须可配置

这是一个游戏，不是博彩协议。链上随机数在本游戏里决定的都是低单位价值、高频的玩法变量（词条、暴击、闪避、敌人突袭、掉落）。操纵一次随机数的期望收益很低，而潜在操纵者要么本就是被信任方（中继器），要么操纵成本极高（验证人）。因此默认策略是「游戏级随机数」：采用**便宜、同步、链上原生**的熵源，而不是昂贵的可验证随机函数（VRF，Verifiable Random Function，可验证随机函数）。但架构上有一条硬要求：**随机数来源必须可插拔、可由运营方配置**——任何场景都能在不改动核心合约逻辑的前提下，切换到更强或更弱的随机源。

#### 2.3.2 架构：IRNG 接口 + RNGRouter 按用途路由

核心合约（CombatEngine、CharacterRegistry、掉落结算等）**不直接触碰任何链上熵源**，而是通过统一接口向 `RNGRouter`（随机数路由器）要随机数：

```solidity
interface IRNG {
    // 同步取数：立即返回一个基于上下文的伪随机数
    function next(bytes32 category, bytes32 context) external returns (uint256);
    // 异步取数（仅 VRF 类 provider 需要）
    function request(bytes32 category, bytes32 context) external returns (uint256 requestId);
}
```

`RNGRouter` 维护「用途 → Provider（随机源提供者）」映射，由管理员配置（未来可移交治理）：

| 用途 category | 覆盖场景 | 默认 Provider |
|---|---|---|
| `COMBAT` | 暴击/闪避/命中、敌人突袭、行动顺序扰动、多段连击的逐段目标抽取 | BlockEntropy |
| `AFFIX` | 角色创建随机：**种族抽取（三层加权 85/12/3）+ 词条随机（方向→词条→档位三次掷骰）** | BlockEntropy |
| `DROP` | 关卡通关道具掉落 | BlockEntropy |
| `MARKET` | （预留）市场类随机 | 按需 |

配置入口就是普通的 `setCategoryProvider(bytes32 category, address provider)` 与 `setGlobalProvider(address)`。每次切换通过链上事件播报，玩家可以审计当前每个用途实际用的是哪个随机源。可选玩法扩展：允许房主建房时为自己的房间选随机档位（例如「混沌模式」纯区块熵、「严肃模式」走 VRF），作为差异化玩法。

#### 2.3.3 内置 Provider 清单

| Provider | 类型 | 熵源 | 成本 | 信任假设 |
|---|---|---|---|---|
| `BlockEntropyRNG`（默认） | 同步 | `keccak256(blockhash(n-1), PREVRANDAO, block.number, block.timestamp, roomNonce, turnId, context)` | 极低（一次哈希） | 验证人仅有轻微偏置能力 |
| `CommitRevealRNG` | 同步（跨回合） | Keeper 每回合先提交（commit）哈希，下回合结算时揭示（reveal）并入熵 | 低（每回合多一次存储写） | Keeper 无法「看到结果再决定」，扣发可见 |
| `KeeperPushRNG` | 同步 | Keeper 每回合直接推送种子 | 最低（随 `advanceTurn` 顺带写入） | 完全信任 Keeper |
| `VrfRNG`（可选） | 异步回调 | 第三方或自建 VRF | 高（两次交易 + 回调） | 信任 VRF 提供方 |

关键工程约束：**回合结算必须是单笔交易的原子操作**（见 §2.4）。前三个同步 Provider 都能保证这一点；异步 VRF 会把一个回合拆成「请求随机数 → 回调 → 结算」三步，Keeper、Bot 与超时判定逻辑随之全部复杂化。这是「默认不用 VRF」最重要的技术理由——不只是省钱，而是保住回合结算的原子性。

#### 2.3.4 Conflux eSpace 链上熵源要点

依据 Conflux 官方 EVM 兼容文档（[evm-compatibility](https://github.com/Conflux-Chain/conflux-documentation/blob/main/docs/espace/build/evm-compatibility.md)）：eSpace 通过 Conflux 改进提案（CIP，Conflux Improvement Proposal）-645 对齐以太坊 EVM 行为；`BLOCKHASH` 可查询范围比以太坊更宽（近 256 块 100 gas，`[n-65535, n-257]` 区间 2100 gas）；`PREVRANDAO` 按以太坊语义可用；且 eSpace 上以太坊型交易只会被打包进高度为 5 的倍数的区块——这与「每 5 个区块一个回合」的节奏天然对齐。上线前需在测试网实测 `PREVRANDAO` 在 eSpace 的具体回填值，若语义存疑可退化为 `blockhash(n-1) + block.timestamp` 混合熵，代价仅为熵来源少一项。

#### 2.3.5 威胁模型：为什么「不安全」的随机数对本游戏够用

对三类潜在操纵者逐一分析。**验证人**：Conflux 采用树图结构权益证明（PoS，Proof of Stake）共识，单个验证人要对特定区块哈希施加偏置，需要在树图分叉中押对参考块，其成本远高于收益（收益不过是游戏里一次暴击或一条词条）。**中继器 Bot**：理论上可以「重掷」（re-roll）——观察到不利的区块哈希就暂扣交易、等下一个块再发。但 Bot 本来就是托管方案（§1.4 方案 C/D）的信任锚，它若要作恶，能做的事情远多于操纵随机数；且扣发会在群聊里表现为可观测的回合延迟，切到 `CommitRevealRNG` 档位可进一步压缩该能力。**自付钱包玩家**（Phase 2 模式）：玩家自己发交易时确实可以挑选发送时机，但结算熵混合的是**包含该交易的区块**的哈希与 PREVRANDAO——玩家在签名时并不知道这个值，无法预判结果，只能靠反复重发去「刷」，而这会被频控与动作费压制。

还有一个容易被误解的要点：**词条随机的真正风险不是「被预测」，而是「被重掷」**——玩家反复重建角色直到刷出极品词条。这是经济学问题而非密码学问题：VRF 同样无法阻止重掷，唯一有效的手段是让每次掷骰子都有成本（重建消耗道具、每日创建/入场上限、动作费），这些已在经济与风控设计中覆盖（见 §6 与 `gameplay-design.md` §7）。因此 `AFFIX` 用途默认也使用 `BlockEntropyRNG`，是威胁建模后的结论而非权宜之计。

### 2.4 战斗结算的确定性
- 合约内战斗必须**确定性**：给定（技能计划 + 行动顺序 + 魔素 + RNG 种子）产出唯一结果。
- 结算分两步更省 gas：**撮合（记录意图）→ 结算（回合结束时一次性计算）**，而非每个动作单独写链。

### 2.5 技能引擎：数据驱动的技能定义（承载复杂度 + 控制 gas 的核心）

技能需求非常复杂：无法手动选目标、单体/多体/全体攻击、**多段连击（一次行动 N 段独立随机目标伤害）**、我方治疗、**护盾（事件型）与伤害乘区（种族技限定）**、控制（眩晕若干回合）、自伤副作用、AP（行动点数）门槛与产出、魔素消耗、**弹药消耗（火枪手按发付费，读改道具数量）**、伤害上限、命中率惩罚（敌我/双方/绝对命中豁免）、**种族伤害修正（查表乘区）**、怪物召唤（需读取战场状态）……这些**不写死在合约逻辑里**，而是全部**数据化**为统一的 `Skill` 结构，结算器只实现**一组有限的原语（primitive）**：

```solidity
struct Skill {
    uint32 id;
    uint8  kind;          // PHYSICAL / MAGIC / SUPPORT / SUMMON(怪物专用)
    uint16 apCost;        // 物理技：施放所需 AP（余额不足 → 失败空过）
    uint16 apGain;        // 物理技：命中后产出 AP
    uint16 ammoId;        // 弹药类技能：消耗的道具类型 id（0 = 无弹药需求，哨兵值；道具 id 从 1 起编、id 0 永不分配，注册层校验）——余额在引擎内部账本（§2.7），非 ERC 余额
    uint16 ammoCost;      // 弹药消耗数量（ammoId ≠ 0 时生效；每次行动固定烧 N 发，与命中数无关，见 §2.5.2）
    uint32 manaCost;      // 魔素消耗；魔素池是**房间（整座地下城）级状态，跨战斗继承、不随单场战斗重置**（gameplay-design.md §5）
    uint8  targeting;     // 目标模式，见下表；targetCount 仅在 MULTI 模式生效，其余模式忽略
    uint8  weightMode;    // 随机权重模式：UNIFORM(均匀) / HP_DEFICIT_ALLY(治疗按血量亏空加权) / THREAT_ENEMY(按敌人威胁权重)
    uint8  targetCount;   // RAND_MULTI_*（不重复目标数）/ RAND_STRIKE_ENEMY（连击段数，≤8）
    uint64 power;         // 伤害/治疗基数（结算时乘属性、防具、随机修正、**种族修正（modRace 查表）**；中间计算 uint256）
    uint64 damageCap;     // 单目标单次伤害上限；0 = 无上限（仅管理员注册的破墙技可设 0，玩家不可获得无上限技）
    uint16 baseAcc;       // 基础命中率（千分比，注册时强制 ≤1000，默认 1000）——数值层可做「重击不稳」类设计，只降不升
    uint8  flags;         // 位掩码：bit0 = GUARANTEED_HIT（绝对命中：跳过命中掷骰，见命中判定管线）
    uint8  modRace[4];    // 种族伤害修正（可选，≤4 条）：匹配目标种族时生效的额外乘区；全 0 = 无修正。修正数值由官方逐技能在注册时填写（引擎只存数据 + 查表，无内置种族克制逻辑，用户定案）
    uint16 modPermille[4];// 与 modRace 一一对应：修正千分比（如 1200 = ×1.2、800 = ×0.8）；伤害公式最后乘入，先于 damageCap 钳制
    Effect[4] effects;    // 固定长度，配 effectCount 使用（类型层防 DoS，注册时强制 count<=4）
    uint8  effectCount;   // 实际 effects 数量（0~4），结算只遍历前 effectCount 条
    SummonRule summon;    // 仅 SUMMON：读取战场的召唤规则
}

struct Effect {
    uint8  op;            // 见下方枚举表
    uint8  duration;      // 持续回合数（控制类），每回合递减
    uint16 magnitude;     // 数值
    uint8  scope;         // 作用目标（自己/被击者/全队/敌全体）
}

struct SummonRule {
    uint16 templateId;    // 召唤出的敌人模板
    uint8  maxCount;      // 单次召唤上限
    uint8  enemyHeadroom; // 场上允许的「敌人超出角色数」裕量（如 +2）
}

struct MonsterAI {
    uint16[8] skillCycle; // 技能循环表（按回合数取模查表；0 = 普攻占位）
    uint8  cycleLen;      // 循环长度（1~8）
    uint8  conditionBits; // 条件位掩码（如 bit0: 魔素低于 X 时跳过大招改普攻）
}

struct EnemyTemplate {
    uint16 aiId;          // 关联 MonsterAI
    uint8  threat;        // 威胁权重（THREAT_ENEMY 模式下的抽取权重；Boss/召唤师设高值；1 = 与均匀等价）
    uint8  race;          // 怪物种族（风味标签）：**不影响怪物自身属性与技能**（模板数值照常填写），仅作为玩家技能 `modRace` 修正的查表键。链上数据本身公开（全文档「不依赖隐藏机制」原则）；「暗藏」仅指战报默认不播报——读链的玩家可提前得知 Boss 种族并选用带种族修正的技能，这是设计允许的信息博弈
    // … 属性、词条等模板字段
}
```

**Effect.op 枚举首版**（可经合约升级追加，每个 op 的叠加/驱散规则随枚举定义固化）：

| op | 效果 | 叠加 | 可驱散 |
|----|------|------|--------|
| STUN | 眩眩：跳过行动 | 同名不叠加，取较长持续时间 | 是（DISPEL） |
| SILENCE | 沉默：无法施放需魔素的技能（普攻/物理不受影响） | 同上 | 是 |
| DMG_OUT_MOD | **伤害乘区·输出侧**：修正**自己造成的伤害**（`magnitude` 千分比，正=增伤）——仅狂暴（兽人）、龙鳞（龙人）两个种族技使用，见 §2.5.2 第 8 条复杂度审查 | 同 op 合并（magnitude 相加，duration 取 max） | 是 |
| DMG_IN_MOD | **伤害乘区·承伤侧**：修正**自己受到的伤害**（正=承伤增加，狂暴「以伤换伤」的代价面）——与 DMG_OUT_MOD 同为引擎**仅有的两个乘区 op**，替代已删除的 DEF_UP/DEF_DOWN | 同上 | 是 |
| SHIELD | **限时护盾**：`magnitude`=护盾量、`duration`=持续回合；伤害结算先扣护盾层（多层独立计时、各自倒计时）再扣 HP；到期未耗完直接消失；**多层扣减顺序 FIFO**（先挂入的先消耗） | 多来源独立计时，不合并 | 是 |
| EVADE_UP | 回避提升（防御方侧的命中惩罚，见命中判定管线） | 多来源叠加，受全局命中下限保护 | 是 |
| ACC_DOWN | **命中率降低**（攻击方侧的命中惩罚，见命中判定管线）：`magnitude`=千分比惩罚、`duration`=持续回合；可由玩家技能/道具或怪物技能施加；作用于施放者的对立方——对敌单体/全体施加、或以 ROOM_ALL 烟幕同时施加于**敌我双方**（含施放者自己） | 多来源叠加，受全局命中下限保护 | 是 |
| GUAR_NEXT | **火枪手「鹰眼」**（红线的唯一豁口，`gameplay-design.md` §4.9）：作用于**自己**，施放时固定 `duration=2`（见下方时序）；期间自己的所有技能跳过命中掷骰。仅火枪手职业技可携带此 op（`SkillRegistry` 注册层校验：仅职业绑定技能表可配，自选池/道具/词条来源禁配）。已存在时**替换** duration（不累加） | 不叠加（已存在则替换持续时间） | 是（敌方 DISPEL 可剥鹰眼，是设计内的反制） |
| DOT | 持续伤害（每回合结算时扣血，走伤害上限） | 各来源独立计时 | 是 |
| HEAL | 即时/持续治疗 | 即时无叠加 | — |
| SELF_STUN | 自伤副作用（施放者自己眩晕 duration 回合） | 同 STUN | 否 |
| DISPEL | 驱散目标身上**标记为可驱散**的效果——对敌施放时剥增益（如 SHIELD、TAUNT），对己施放时净化负面（如 STUN、DOT）；驱散哪些方向由技能的 `targeting` + effect 配置决定 | 即时 | — |
| TAUNT | 嘲讽：被嘲讽者的**单体攻击**（`RAND_SINGLE_ENEMY`）随机目标强制重定向为嘲讽者；**多体/全体攻击不受影响**（防双坦吸干全部伤害，`gameplay-design.md` §4.8）；嘲讽者若出现在多体目标列表中则正常受击（不豁免）；**嘲讽者死亡时 TAUNT 立即失效** | 互斥（后者覆盖） | 是 |
| LIFESTEAL | 吸血：按本次伤害的一定比例治疗施放者（恶魔种族技「汲魂」、嗜血词条） | 即时，随攻击结算 | — |
| MANA_DELTA | **魔素池操作**：`magnitude` 为正=注入（白魔法师「圣泉」）、为负=抽毁（敌人「魔素泄漏」「魔素虹吸」）——操作的是房间级魔素池而非角色 | 即时 | — |
| STUN×P | 概率控制：Effect 概率字段 <1000 时结算掷骰（盾击眩晕、暴风术**每段独立**掷骰、缠绕束缚）；默认 1000=必中——复用 STUN/DOT 等 op + `Effect.prob` 字段（默认必发） | 同所附 op | 同所附 op |

**内容层新增原语登记**（`content-design.md` §10，全部小~中等改动、不触碰三大架构红线）：① `Skill.hpCost`（黑魔法师「献祭」以命换多段攻击，与 AP/魔素/弹药同入两阶段门槛）；② SUMMON 扩展玩家侧（白魔法师「替身人偶」假目标：有血量、无行动、计入我方随机目标集稀释敌方命中、**不参与收益分配、不占玩家名额、无法嘲讽**、占房间单位总数上限——复用召唤槽预分配机制）；③ 上表 MANA_DELTA / LIFESTEAL / `Effect.prob`（圣泉=治疗+魔素注入的**一技能多效果**，由现有 Skill 结构承载）；④ **DMG_OUT_MOD / DMG_IN_MOD** 两个伤害乘区 op（狂暴、龙鳞——同时删除 DEF_UP/DEF_DOWN，见 §2.5.2 第 8 条审查）；⑤ 弹药道具两档（铅弹/龙击弹，`ammoId` 字段天然支持，ItemRegistry 多注册一种）；⑥ 复活原语（「不死鸟之羽」，预留、经济敏感可后置）。引擎 op 净变化 = +2 −2。

### 2.5.1 活跃效果（ActiveEffect）：运行时状态模型

`Effect[4]` 是**技能定义层**；技能命中后效果**落到角色身上**，运行时状态用独立的固定数组存储：

```solidity
struct ActiveEffect {
    uint8  op;            // 与 Effect.op 同一枚举
    uint8  duration;      // 每回合结算时 -1，归零即移除
    uint16 magnitude;     // 剩余数值（盾的剩余量 / DOT 每跳量等，按 op 语义使用）
    uint16 sourceId;      // 来源（技能/道具 ID，战报播报用）
}
// 存储于角色战斗状态内：ActiveEffect[6] effects（固定 6 槽，足够容纳 4 条技能效果 + 道具/词条来源）
// 满 6 槽时新效果被**拒绝**（该条 effect 落空，技能其余效果照常结算）——容量是类型层硬上限，保证回合遍历 gas 有界
```

- 结算顺序：每回合行动者结算前，先遍历自身 ActiveEffect 处理 DOT/倒计时；伤害结算时遍历 SHIELD 层（FIFO 扣减）；死亡时整组清除。
- **同 op 合并规则（可叠加类）**：`ACC_DOWN` / `EVADE_UP` 这类「多来源叠加」的 op，**同一角色的同一 op 只占一槽**——新来源施加时 `magnitude += 新值`、`duration = max(原剩余, 新持续)`。独立计时类（SHIELD、DOT）才各占一槽。由此 6 槽足以容纳「烟幕 + 致盲 + 道具」三重 ACC_DOWN（合并为 1 槽）+ 护盾 + DOT + 控制，不会被叠加惩罚挤爆。
- 每回合最坏遍历：≤10 角色 × 6 槽 = 60 次常数操作，gas 有界。

**targeting 模式与目标选择规则**（玩家只传技能 ID，目标一律由结算器决定；**不允许任何手动指定目标**）：

| 模式 | 目标选择规则（全部随机，按 `weightMode` 加权） | targetCount |
|------|--------------|-------------|
| RAND_SINGLE_ENEMY | 从存活敌人中**随机 1 个**（RNG 决定） | 忽略 |
| RAND_MULTI_ENEMY | 从存活敌人中**随机 N 个不重复** | 生效 |
| RAND_STRIKE_ENEMY | **多段连击**：N 段独立伤害实例，**每段独立抽取随机目标（可重复命中同一目标）**、独立命中掷骰、独立伤害上限——连射/乱舞类技能；`targetCount` = 段数（注册时硬上限，如 ≤8）；AP/魔素/弹药按**行动整体**扣一次，不按段数重复扣；effects 逐段独立施加（同 op 叠加遵循合并规则） | 生效 |
| ALL_ENEMY | 全部存活敌人（无随机性） | 忽略 |
| RAND_SINGLE_ALLY | 从存活我方（含自己）中**随机 1 个** | 忽略 |
| RAND_MULTI_ALLY | 从存活我方中**随机 N 个不重复** | 生效 |
| ALL_ALLY | 我方全体（含自己） | 忽略 |
| ROOM_ALL | **场上全体存活单位（敌我双方，含施放者）**——烟幕/天候类场地效果专用 | 忽略 |
| SELF | 自己 | 忽略 |

- **weightMode 加权随机**（默认 UNIFORM 均匀）：`HP_DEFICIT_ALLY` 按目标当前血量亏空加权（治疗技默认推荐——残血更可能被奶到但非必然）；`THREAT_ENEMY` 按 `EnemyTemplate.threat` 加权（Boss/召唤师更可能被打到但非必然）。加权抽取仍是**随机**，玩家不可指定；权重全 1 = 均匀。加权使治疗/输出的期望贡献可预估（排技能有决策依据），同时保留方差（戏剧性时刻）。
- 随机目标消耗 RNG 调用（走 `RNGRouter`，见 §2.3）——目标随机性与暴击/闪避共享同一随机源体系，是「运气权重」（`gameplay-design.md` §3.1）的实现载体。
- **TAUNT 交互**：单位身上存在 TAUNT 效果时，其**单体攻击**的随机目标被强制重定向为嘲讽者（多体/全体不受影响；见 Effect 表 TAUNT 行）——唯一的确定性目标干预。
- 随机选择的 gas 成本：从 ≤10 个候选中加权抽取是 O(候选数) 的简单循环 + 一次 RNG，无 gas 风险。
- **收益随机分配**：结算时对每个存活者从 RNG 取随机权重，按权重瓜分奖池（`gameplay-design.md` §6.1）——同一结算交易内完成。

#### 命中判定管线（用户定案：命中修正**只降不升** + 绝对命中豁免）

结算器在**选定目标之后、结算效果之前**执行命中判定，规则固定为三层：

1. **豁免掷骰（以下四种情况直接命中，不消耗 RNG）**：
   - `targeting` 为我方系（`RAND_*_ALLY` / `ALL_ALLY` / `SELF`）——**对我方的治疗与增益永远绝对命中**（奶不 miss）；
   - `targeting` 为 `ROOM_ALL`——场地效果（烟幕等）必生效；
   - `flags.GUARANTEED_HIT`——技能固有的**绝对命中**（无视一切命中惩罚），配给少数特殊攻击技。
   注意：**绝对命中 ≠ 指定目标**——目标仍按随机规则选取（§4.2 原则不变），「绝对」只保证「选定后不会落空」；
   - 攻击者身上存在 `GUAR_NEXT` 活跃效果（火枪手「鹰眼」，见 Effect 表）——其**本轮所有技能**跳过掷骰。
   **GUAR_NEXT 时序（精确语义）**：鹰眼在回合 N 施放（施放即占行动位，当回合不再有该火枪手的其他行动）；`duration=2` → 回合 N 结算时递减为 1（仍存活）；**回合 N+1 全程有效**（期间其所有技能跳过掷骰）；回合 N+1 结算时递减为 0，移除。若火枪手在回合 N+1 被眩晕（跳过行动），该效果**自然浪费**（回合结束照常递减归零）——这是设计内的打断代价。
2. **掷骰判定（敌方系攻击技，逐目标独立掷骰）**：
   `命中概率 = baseAcc − Σ(攻击者身上 ACC_DOWN) − Σ(防御者身上 EVADE_UP)`，向下钳制到**全局命中下限**（配置常量，如 50‰，官方可调）——堆满惩罚也不会出现绝对打不中。
   「攻击者身上」指**本次实际行动的单位**，「防御者身上」指**本次被选中的目标单位**——ACC_DOWN 挂在谁身上谁开枪受罚，EVADE_UP 挂在谁身上谁更难被打中。
   每个目标一次 RNG 调用（`COMBAT` 用途，与暴击/闪避同路由，§2.3）；多目标技逐个掷骰，gas 上限 = 目标数 × 常数。
   **ROOM_ALL 烟幕的时序**：效果在施放者行动结算时立即挂到全体——按敏捷序，**先于施放者行动的单位不受本次烟幕影响，晚于施放者的单位本回合即受影响**；高敏捷施放者天然获得「先开枪再蒙烟幕」的时序优势，这是敏捷价值的组成部分（设计内，无需额外机制）。
3. **未命中的后果**：伤害与效果全部落空，但**已支付的 AP/魔素不退还**，物理技的 `apGain` 也拿不到（本就是「命中后产出」）——命中率惩罚的战术价值就是让敌人**白花钱空过**。
- **设计红线（引擎层固化，用户定案含唯一豁口）**：枚举中**不存在任何通用提高命中率的 op**；`GUARANTEED_HIT` 只能由技能注册时固有配置，**无法通过任何技能/道具/词条在战斗中获得**。命中经济学只有「变差」与「豁免」两态，没有「变好」——**唯一例外**：火枪手职业的 `GUAR_NEXT`（鹰眼，`gameplay-design.md` §4.9），它是职业本体而非通用增益，注册层强制四道闸：仅职业技能表可配、仅作用于自己、以行动成本付费（鹰眼回合无输出）、可被控制与驱散反制。实现上它是一个普通 ActiveEffect op + 命中管线一条豁免分支——代码并不脏，「脏」的只是红线上的这道刻意的口子。

#### 2.5.2 设计原则与各需求的落地方式

1. **不允许指定目标 → targeting 全随机（可加权）**：合约按 `targeting` 模式 + `weightMode` 从合法目标集合中抽取目标（RNG 决定，玩家不可指定），**玩家排技能时只需给技能 ID，无需给目标参数**，calldata（调用数据）极小，也天然杜绝「背刺残血挂机队友」类指令歧义；随机目标是运气权重的核心载体（`gameplay-design.md` §3.1）。
2. **AP / 魔素 / 弹药三重门槛（两阶段模式，实现红线）**：**Phase 1 只读检查**——`apCost` vs 角色 AP、`manaCost` vs 房间魔素池、`ammoId≠0` 时引擎**内部账本的弹药余额** vs `ammoCost`（§2.7）；**Phase 2 全部通过后才依次扣减**——AP（战斗状态）、魔素（房间池）、弹药（内部计数器 −N，掉落即「铸造」进账本、消耗即核销）。**任一不足则零扣减、失败空过**（写一个事件即可）。三项资源**全部位于引擎自身 storage**——检查与扣减都是本地 SLOAD/SSTORE，**无任何跨合约调用**（这比原 ERC-1155 钱包直扣方案更快，两阶段红线也更易满足）。**弹药在扣减时即核销，之后即使 miss 也不退还**（与 AP/魔素同语义：枪响子弹就没了）。
   - 弹药余额与扣减都在**引擎内部账本**（§2.7）——同交易内的 `giveItem`（递弹药）按标准交易顺序生效：同区块先到的递弹交易先入账，本回合结算即用得上。
   - **左轮弹雨语义（消歧）**：`ammoCost=N` 表示**每次行动固定烧 N 发**，与命中目标数无关（命中 3 个还是 0 个都烧 N 发）；**不存在「逐目标逐发消耗、中途弹尽」模式**——弹尽即整次行动在 Phase 1 失败空过。
   - **计划条目消耗 ≠ 资源扣减**：弹尽/资源不足空过时，`SkillPlan` 队列指针照常推进（该回合条目被消耗、`len--`），但三种资源零扣减——空过是「技能效果落空」，不是「排技能失败」。
   - gas：三重门槛全部本地 SLOAD/SSTORE，合计 < 1 万 gas/行动，**比 AP/魔素本身还便宜**（原 ERC-1155 钱包直扣方案的跨合约调用已消除）。
   - **递弹药（弹药不是房间状态）**：任何人可随时 `giveItem(火枪手, 子弹id, N)`——引擎**内部账本转账**，一笔极便宜交易，不占任何人的行动位、无需对方操作（§2.7）——「给火枪手递子弹」是设计内的社交协作（`gameplay-design.md` §7.2）。
3. **伤害上限**：`damageCap` 在伤害公式最后一步 `min(damage, cap)`，同时给了打包空间——HP 与伤害都可用 `uint64` 以下整数存储，**一个 `uint256` slot 打包多个战斗字段**。**多段连击技的每段独立钳制**（`RAND_STRIKE_ENEMY`，N 段 × 每段上限 = 总输出上限，段数由注册时 `targetCount` 封顶 ≤8）。
4. **种族伤害修正（查表乘区）**：伤害公式乘入 `modRace/modPermille` 查表结果（目标种族命中条目则 ×对应千分比）——引擎**只做 ≤4 条的线性查表**，克制关系与数值完全由官方逐技能注册时填写，无内置种族克制逻辑（用户定案）。查表 ≤4 次比较，gas 可忽略。
5. **召唤读取战场**：结算器在执行 `SUMMON` 时数一遍存活敌人数 E、存活角色数 P，若 `E >= P + enemyHeadroom` 或达房间单位总数上限则**召唤落空**；否则召唤 `min(maxCount, P + enemyHeadroom - E)` 个。全程只有计数循环，无额外存储。
6. **控制/增益（眩晕、护盾、回避）**：都是 `Effect` 列表里的 `op`，带 `duration` 递减；行动前先扫一遍自身 Effect 列表决定是否跳过（眩晕）。**每个技能的 effects 数量硬上限（例如 ≤4）**，保证单次结算 gas 有界。
7. **怪物技能**：怪物同样是 `Skill` 的消费者。怪物 AI（人工智能）不写代码，数据化为**技能循环表**（如 [普攻, 普攻, 召唤, 大招] 循环 + 少量条件位），结算器按回合数取模查表。
8. **伤害乘区与属性修正的复杂度审查（用户定案：避免临时加减防御力的技能）**：
   - **两种效果范式**：事件型 op（STUN/SHIELD/TAUNT/ACC_DOWN/EVADE_UP/DOT/LIFESTEAL/MANA_DELTA/SUMMON）改变**离散事件**——每个 op 的结算逻辑独立封闭、互不组合，新增事件型技能对结算器是**零改动**（纯数据注册）；其中命中系（ACC_DOWN/EVADE_UP）走**纯加法管线**（`命中率 = baseAcc − ΣACC_DOWN − ΣEVADE_UP`，一次槽遍历加总），是最廉价的一类。属性修正型 op 修改伤害公式的**连续乘区**——单个实现是小改，但复杂度**随使用数量超线性增长**（叠加语义矩阵「取最大/相加/相乘/覆盖」要逐 op 定义并测试，组合数平方级；若再分物攻/魔攻修正则 op 与公式分支翻倍；与静态词条乘区的顺序交互要专门定义；战报每次伤害要播报完整乘区链，gas 与可读性双降；数值校准工作量同步平方级膨胀）。
   - **结论：少量可控，大量显著复杂**。采纳避免方向——引擎只保留 `DMG_OUT_MOD` / `DMG_IN_MOD` 两个**通用伤害乘区 op**（删除 DEF_UP/DEF_DOWN），**修正伤害而非修正属性**：与 `modRace` 同处伤害公式尾部的统一乘区（`damage = power × 属性 × modRace查表 × (1+ΣDMG_OUT_MOD攻方) × (1+ΣDMG_IN_MOD守方) → damageCap`），不区分物理/魔法——实现为结算时遍历攻守双方 ActiveEffect 槽位加总后各一次乘法（O(12) 常数遍历，gas 可忽略）。
   - **内容层封顶**：乘区 op 的使用者**仅 2 个种族技**（狂暴=OUT正+IN正；龙鳞=SHIELD+OUT正），种族技数量被种族数硬性封顶，乘区语义规模天然有界；**职业技能与自选池零乘区技**——防御面统一 SHIELD（事件型先扣层：磐石之躯已从减伤改为护盾），命中面统一 ACC_DOWN/EVADE_UP（加法管线：守卫「回避」只提回避，黑幕/深渊低语/尘幕同理）。设计表达力几乎无损（「变硬」=护盾、「变闪」=回避、「削弱敌人」=命中率惩罚），损失的只有「百分比减伤」手感（由护盾的等效吸收近似），换来乘区语义的规模上限与校准成本的大幅收窄（内容侧分析见 `content-design.md` §10.1）。

#### 2.5.3 gas 预算的量级论证

| 项 | 成本来源 | 约束 |
|----|----------|------|
| 单回合结算 | 遍历在场单位 × 每人 1 技能 × ≤4 effects | 在场单位上限（角色上限 + 敌人上限，建议双方各 ≤10）→ 最坏 ~25 单位 × 常数运算 + 少量 SSTORE（血量/魔素/AP 变更），估算 300k~800k gas |
| 排技能 | 1~2 个 SSTORE（计划打包进 slot） | 前瞻 N ≤ 16，每回合技能 ID 用 uint16 编码后 16 个也只占 1 slot |
| 召唤 | 复用预留的敌人槽位（房间创建时按敌人上限**预分配**数组），无动态扩容 | 敌人槽位预分配，召唤只是「激活已预留槽位」，避免运行时扩容数组的昂贵 SSTORE |
| 事件输出 | 每行动 1 条事件 | 战报细节放事件（链下 indexer 渲染），不占 storage |
| 命中/目标 RNG | 最坏约 200 次 RNG 调用/回合（10 单位 × 最多 8 段连击 × 每段目标抽取 + 命中掷骰 + 收益分配） | BlockEntropy 是纯视图逻辑（keccak256，无 SSTORE），单次约 30 gas，合计 < 7k gas，可忽略；miss 路径提前终止，实际通常远低于最坏值 |
| 弹药消耗 | 引擎内部账本 SLOAD/SSTORE（无跨合约调用） | < 1 万 gas/行动，比 AP/魔素扣减更便宜；弹尽空过只写事件，最便宜 |

事件中命中类动作附带 `guaranteed` 标志位（来源 = GUARANTEED_HIT / GUAR_NEXT / 我方系豁免），indexer 据此在战报中区分「鹰眼命中」与普通命中。

结论：最坏回合结算远低于 eSpace 单块 3000 万 gas 上限的一半，且有硬上限保证**不会因召唤失控或房间人数而 gas 爆炸**。

#### 2.5.4 可扩展性
- 新技能 = 在 `SkillRegistry` 里**注册一条新数据**，不改结算器代码。
- 新效果类型 = 给 `Effect.op` 枚举加一个原语（小改，走合约升级）。
- 结算器保持小而可审计，复杂度被「数据多、原语少」的原则封在配置层。

### 2.6 技能计划（SkillPlan）：前瞻排程的链上表达

「排技能」不是聊天口述，而是**明确的链上状态**。每个角色在房间内的计划用固定长度结构存储（**杜绝动态数组**）：

```solidity
struct SkillPlan {
    uint16[16] queue;    // 前瞻队列；实际首元素在 queue[startIdx]
    uint8   len;         // 实际长度 0~16（前瞻 N ≤ 16 硬上限）
    uint8   startIdx;    // 环形首指针：消耗后 +1 而非真实移位，省 SSTORE
}
// 存储：mapping(roomId => mapping(playerId => SkillPlan))
// queue 打包占 2 个 slot，len/startIdx 挤进相邻字段，覆盖写只花 ~2 SSTORE
```

**生命周期语义（全部在合约层强制）**：
- **提交/覆盖**：`setPlan(uint16[16])` 一次性覆盖整条队列——玩家改计划永远是「以新换旧」，无增量 patch 歧义；提交者必须是角色拥有者（**只能给自己排**，队长也不例外）。
- **消耗**：`advanceTurn()` 结算时按行动顺序取每个角色 `queue[startIdx]` 执行；执行后 `startIdx++`（环形指针，不真实移位），`len--`。
- **取消**：`cancelPlan()` 把 `len` 置 0——只支持**整体取消**，不支持部分取消（规则从简；要改就重新提交完整队列）。
- **执行不校验前置状态（设计内）**：队列执行时**不检查**前置效果是否仍有效——火枪手排「鹰眼 → 弹雨」两步计划后，若鹰眼被 DISPEL 剥掉或开火回合被眩晕，队列中的射击技仍照常执行（可能 miss 或空过）。计划是对未来的**承诺而非保证**，被拆解的风险由玩家自行评估——这正是「混乱与运气是乐趣核心」在排程层的体现（`gameplay-design.md` §4.3）。
- **回合快照**：`advanceTurn()` 的交易内计划消耗以**该交易执行时刻**的链上状态为准；同区块内先到的 `setPlan` 生效、后到的下回合生效（区块内交易顺序即最终顺序，无歧义）。
- **道具使用（用户定案）**：作为特殊「技能 ID」（保留段，如 id ≥ 0xF000）排进同一队列，结算时转给道具逻辑——**使用道具占用该回合的行动位，用了道具当回合就不能再使用技能**（一个队列管一切行动）；**不限每场战斗的使用次数**（`gameplay-design.md` §7.2 定案：次数不限制，代价是占行动位——回合数本身就是天然上限）。
- **怪物无队列**：怪物不吃 SkillPlan，按 `MonsterAI.skillCycle` 取模行动（§2.5）。

### 2.7 道具资产层：只用 ERC-20（带 Permit）与 ERC-721，不用 ERC-1155（用户定案）

**标准选型**：道具分两类资产形态——消耗品/弹药是**同质化、可堆叠**资产 → 每类一个 **ERC-20 道具币**（`ItemFactory` 克隆部署，decimals=0 整数计数，模板内置 **ERC20Permit**）；角色与未来的「独特物品」（有独立身份/履历的稀有掉落）→ **ERC-721**。全系统**不使用 ERC-1155**——钱包、水龙头、市场等生态工具对 ERC-20/721 的支持最广。

**两层账本（approve 问题的结构性解法）**：道具余额有「游戏内」与「钱包」两种形态，边界清晰：
- **游戏内余额 = CombatEngine 内部账本**（`mapping(playerId => mapping(itemId => uint))`，与 AP/魔素同层的引擎 storage）。**游戏的全部循环都不碰 ERC-20**：地下城掉落直接记账、商店购买（扣 Economy 游戏币）直接记账、战斗消耗/弹尽判定直接读写计数器、**「给火枪手递子弹」= 引擎内部转账 `giveItem(队友, itemId, N)`（纯 SSTORE 挪动，~2 万 gas 一笔，无需对方任何操作）**——游戏内流转**零 approve、零 permit、零外部调用**。
- **钱包形态 = ERC-20 道具币**，仅在**外部交易**（场外 OTC、未来 DEX 挂单）时存在。出入边界两个函数：
  - `withdrawItem(itemId, N)`：内部余额 −N，引擎按 MINTER 角色 `mint` 给玩家钱包；
  - `depositWithPermit(itemId, N, deadline, v, r, s)`：玩家链下签 **EIP-2612 permit** 授权引擎，**一笔交易完成 approve + transferFrom + 入账**（引擎按 BURNER 角色 `burn` 销毁钱包币）——存回游戏**永远不需要单独的 approve 交易**；钱包里直接 `approve(MAX)` 一次性永久授权亦可（引擎是不可升级核心合约，风险面仅为道具本身）。
- 链上 ERC-20 `totalSupply` 恒等于「钱包流通量」，游戏内余额不出现在任何 ERC-20 里——账目天然清晰。

**approve 场景全表**（为何「反复 approve」不成立）：
| 场景 | 是否涉及 approve |
|------|----------------|
| 商店买道具（游戏币支付） | 否（Economy 内部账本） |
| 战斗用道具 / 引擎烧子弹 | 否（引擎内部账本） |
| 递弹药给队友 | 否（引擎内部转账） |
| 钱包 ↔ 场外交易（ERC-20 transfer） | 否（transfer 不需授权） |
| 从钱包存回游戏 | **permit 折叠进同一笔交易**（或一次 approve(MAX) 永久解决） |

**与 ERC-1155 方案的对比**：结算扣弹从跨合约调用（~30~50k gas）降为引擎内部 SSTORE（~5k）；ERC-20 的 transfer **没有接收回调**（重入面比 1155 的 `onERC1155Received` 更小，§6.0）；代价是道具类型多了要多部署克隆合约（~5 万 gas/类，一次性）。

## 3. 回合驱动服务（Keeper）

合约无法自己定时执行，必须由外部触发。两种结束模式对应：

- **自动回合**：一个 **Keeper 服务**（官方 Bot 与队长 CLI 均可担任，见 §1.5）监听区块/时间，达到「5 区块或 15 秒」即调用 `CombatEngine.advanceTurn()`。
- **手动回合**：任何玩家指令直接调用 `advanceTurn()`。

### 3.1 竞态与滥用防护（合约层强制）
- **`turnId` 单调推进 = 天然互斥**：同一房间的同一回合，只有**第一笔成功交易**能推进 `turnId`；并发的手动/自动交易中后来者在 `require(turnId == expected)` 上 revert（状态零变更，仅浪费调用者自己的 gas）。手动与自动无需区分处理，二者是同一个入口。
- **推进冷却**：每次推进记录 `lastAdvanceBlock`，`advanceTurn()` 要求距上次推进 ≥ 2 区块——任何人（包括恶意 CLI）都无法高频刷推进；冷却内的调用直接 revert。
- **手动推进不受「等满 5 区块」约束**：手动提前结束是玩法特性；推进后自动计时的基准重置，Keeper 重新等 5 区块。
- **Keeper 单点故障兜底**：合约不指定唯一 Keeper——**任何人**在「距上次推进 ≥ 30 区块」（远超正常回合窗口）后都可调用 `emergencyAdvance()` 推进回合（该函数只推进回合与超时判定，不含任何特权）。官方 Keeper 挂掉时，玩家的 CLI 或任何脚本都能解卡；正常节奏下 emergency 入口因 30 区块门槛而不可用。
- **超时判定随推进执行**：超时失败/房间过期检查内嵌在 `advanceTurn()` 中（推进时顺手检查），无需单独触发器。
- Keeper 同时也是 **预言机价格刷新**（§5）与 **超时/超回合失败判定** 的触发者。

## 4. 客户端：Discord / Telegram Bot 与自托管 CLI

### 4.1 身份映射（三种通道，一个 playerId）
- `chatUserId → playerId`（链上 uint/address 映射），首次聊天指令时由 Bot 注册。
- Bot 持有中继钱包，代 L1 玩家发交易并付 gas；聊天消息即「授权」。
- L2 玩家通过 CLI 钱包签名验证码，把钱包地址绑定到**同一个 playerId**（见 §1.5），此后两条通道混用。
- 合约层对三类通道一视同仁：都只是「某个 playerId 的指令」，只有「排技能只能排自己的」这类归属校验（§2.5）。

### 4.2 命令示例（群内文字）
```
/创建角色 职业=法师          （或 职业=无）
/开房 难度=D2                （返回房间号，或 /开房 难度=D2 #42 自指定）
/加入 #42
/排技能 鹰眼 弹雨 接下来2回合
/取消计划
/结束回合
/进入下一场战斗              （仅队长，上一场获胜后）
/全员逃离                    （仅队长，某场战斗获胜后）
/逃离                        （个人，延迟离场）
/买入大头菜 100
/卖大头菜 50
/状态                        （Bot 拉链上状态渲染战报）
```
CLI 通道提供等价的子命令（`zg join 42`、`zg plan eagle-eye revolver 2` …），并额外带 `--announce` 自动回写聊天频道（§1.5）。

### 4.3 索引与展示
- Bot 跑一个轻量 **indexer**（监听合约事件），把 room/turn/combat 结果转成群内可读文本/表格，弥补链上只存权威状态、不存「好看」数据的短板。**弹药余量预警**：indexer 监听引擎内部账本事件与 SkillPlan——当火枪手弹药余额低于已排计划的剩余弹药总需求时，自动在频道播报预警（纯链下提示，不改链上状态）——「谁去给火枪手递几发子弹」成为群内协作信号。
- 队长 CLI 可开启**主播模式**接管本房间战报（同一事件流、同样的渲染模板），官方 Bot 检测到房间已有主播则自动让位，避免重复播报。

## 5. 预言机与「大盘」

- `Oracle` 合约保存 CFX 价格；由 **受权地址**（官方 Keeper）按最小刷新间隔（如 4 小时）调用 `updatePrice()`（链下取价 → 上链）。
- **防抢跑/防操纵（三层）**：
  1. **更新与结算同笔原子完成**：`updatePrice()` 在同一笔交易内完成「写入新价 → 按 新价/旧价 变动率结算全部多空头寸 → 结算失衡费」三步。玩家**无法在看到新价后、结算前插入交易**——刷新交易的执行顺序只决定结算发生在哪一笔交易里，玩家没有可插队的中间态。市场在结算完成前处于暂停（`settling` 标志），结算期间开/平仓一律 revert。
  2. **价格异常带**：新价偏离旧价超过带宽（如 ±50%）时拒绝更新并保持旧价、触发人工检查——防预言机源被黑后瞬间抽干多空池。
  3. **多源 median 升级路径**：初期单源（官方），后续接入 Chainlink Data Feed（若 eSpace 有 CFX feed）或自建多源中位数。
- **Market（多空对赌）结算细节**：每个头寸记录 `openPrice`（开仓锚定价）与锁定游戏币；刷新结算时按 `新价/开仓价` 变动率在多空双方锁定金之间转移（杠杆为 1，无爆仓穿仓问题——最坏亏光自己锁定的本金，池子恒守恒）；点差与失衡费在结算中一并收取并销毁。
- 价格刷新后在群内播报「当前市值」与各方盈亏变动。

> 多空对赌模型下，预言机刷新不再有「兑付义务」（所有支付来自玩家锁定本金，见 `gameplay-design.md` §7.3），预言机操纵的收益上限被结构性压低——操纵者最多赚走对手方的锁定金，还要先持有头寸付点差。

## 6. 安全与风控

### 6.0 重入防线（道具/弹药场景专项）
- **战斗消耗路径零外部调用**：弹药/道具扣减全部在引擎**内部账本**（§2.7）——结算调用链上没有任何外部合约交互，不存在受攻击者控制的代码执行点。
- **递弹药路径无回调面**：`giveItem` 是引擎内部转账（纯 SSTORE）；唯一涉及外部代币的 `depositWithPermit` / `withdrawItem` 走标准 ERC-20 **transferFrom / mint——ERC-20 没有接收回调**（对比 ERC-1155 的 `onERC1155Received`，重入面天然更小）。
- **纵深防御**：CombatEngine 所有状态变更外部函数统一加 `nonReentrant` 守卫 + 遵循 CEI（先检查、后效果、最后交互）顺序——即使未来引入带回调的外部交互（如第三方支付代币），回调重入也只会撞上守卫 revert。
- **角色在房间内时 transfer 被 CharacterRegistry revert**（§2.1）——合约钱包也无法通过「战斗中转移角色」破坏弹药归属一致性。

### 6.1 中继器（Bot）权限模型
- Bot 代发的每笔交易**必须来自该玩家的明确聊天指令**，指令原文哈希随交易上链（审计可回溯）；Bot 无自有游戏操作权限。
- **速率限制**：每 playerId 每分钟动作数上限（合约层 `Limits` 同步校验，双保险）。
- **防冒充**：严格绑定 chatUserId → playerId；绑定变更需双通道确认（旧通道 + 新通道各一次）。
- **Bot 无排他性**：任何房间任何人可随时切到 CLI 通道自付直发；Bot 作恶的影响被「指令可审计 + 通道可切换 + 链上状态权威」三重限制。

### 6.2 治理与可升级性
- **资产不可升级**：角色 NFT、道具 ERC-20 币与工厂、`Economy` 账本为不可升级合约（只加不可变逻辑），所有权数据永不被升级逻辑触碰。
- **逻辑可升级**：`CombatEngine`、`SkillRegistry`、`Market` 等用可升级代理；升级权限归**多签（如 3/5）+ 48 小时时间锁**，时间锁内升级计划公示于链上事件，玩家可审计甚至提前撤离资产。
- **紧急暂停**：多签可全局暂停（Pausable）——用于漏洞应急；暂停期间战斗冻结但资产安全，恢复需再次多签。
- **配置类函数**（难度参数、税率、限额、RNG Provider）单独走 **TimelockController 短时间锁（如 8 小时）**，改配置无法突袭。

### 6.3 全局硬上限与限额（合约常量/可调参数上限）

| 项 | 上限 | 目的 |
|----|------|------|
| 单房间同时在场单位 | 角色 ≤10 + 敌人 ≤10 | 结算 gas 有界 |
| 技能 effects 数 | `Effect[4]` 固定数组 | 类型层防 DoS |
| 前瞻计划长度 | 16（`uint16[16]` 固定） | 存储/gas 有界 |
| `SkillRegistry` 注册总数 | ≤1024 | 防垃圾注册 |
| 同时存活房间数 | ≤1000 | 状态膨胀控制 + 房间过期回收 |
| 单回合事件数 | ≤64（超出合并为摘要事件） | 索引器/战报可用性 |
| 预言机刷新 | 最小间隔 4h + 受权地址 | 防高频操纵 |
| 管理操作 | 时间锁（升级 48h / 配置 8h） | 防治理突袭 |

### 6.4 开放链上经济的安全边界（防 Sybil / 防信息滥用 / 防税基绕过）

游戏跑在开放区块链上，必须承认三个**不可防御事实**，并把强制力只放在**合约入口**：

1. **无限账号（Sybil 不可防）**：无 KYC（Know Your Customer，实名认证）的开链环境里，工作室可开无限多账号。一切按账号的限额（入场次数/购币/开仓/打工）都是**软约束**，会被多号稀释。硬防线有三条：
   - **gas 经济压制**：每次链上动作都有真实 CFX 成本。CLI 自付通道天然如此；设计上保证**单账号单动作的期望可变现产出 < 其 gas 成本**（打工奖励校准低于打工 gas；道具掉落与强度使刷号的期望收益低于规模化 gas 开销）。
   - **Bot 通道配额封顶补贴**：官方代付的 L1 通道按账号设每日动作配额——补贴总量的上限 = 配额 × 账号数，配额收紧即可控；Bot 对异常模式（同 IP 段、同节奏批量操作）可做链下风控（Bot 是中心化服务，这是它的天然权利与义务）。
   - **可转移资产价值有天花板**：道具强度上限 + 极品角色被「重掷道具商店价」套利锚定（§7.4）——工作室能刷出的东西单件价值有限，规模化利润空间被封顶。
2. **信息不可屏蔽**：链上状态任何人可读。**词条、仓位、敌人配置、掉落率、技能循环全部公开**——设计不依赖任何「隐藏」机制（无售前隐藏、无盲盒依赖）；博弈全部按公开信息设计（多空公开对赌、技能循环可查）。
3. **转移环节半可强制**：链上改变资产 owner 的**唯一途径**是官方 NFT/ERC-20 合约的 transfer 系函数（approve 只是授权、不转移所有权，无旁路）——因此**与价格无关的转移规则（等级重置、固定费、冷却）可在 NFT transfer / ERC-20 的 `_update` 钩子内 100% 强制**（角色等级重置即用此法，`gameplay-design.md` §7.4）。不可强制的只有**按成交价百分比抽税**（成交价与支付可完全留在链下），经济模型对此零依赖。道具当前保持零转移限制，需要时可在 ERC-20 的 `_update` 钩子随时加规则。
4. **游戏币与大头菜账本是强强制层**（对我方有利）：二者均非代币，是合约内部 mapping，无 transfer 接口、无场外交易可能（无法把 mapping 条目交给别人；托管账号共享等于交出全部资产）。主水龙头（打工/通关收益）全部沉淀在这一层，通胀锁死在不可转账层内；美元购买只走官方商城单向入金。

**GasTreasury 的诚实定位与付费回收模型**：中继 Bot 的 CFX 成本回收**主力是 L1b 充值计费**（玩家直接付 CFX/美元，覆盖 gas + 服务费，见 §1.5 三层通道表），而非游戏币动作费。动作费（游戏币）的真实作用是**链上层的防刷摩擦与速率限制第二道闸**（对 Bot 通道和直连通道一视同仁），**不构成 CFX 回补闭环**（游戏币没有链下变现通道）。L1a 免费配额是获客支出，被配额硬性封顶；补贴总量的现实控制 = L1a 配额 × 账号数 + Bot 链下风控 + 持续引导用户向 L1b/L2 迁移。

### 6.5 CLI 播报防伪造
- CLI 发往聊天频道的**声明类消息**（「我排了技能」）必须附带：动作的**链上交易哈希**（已确认上链）或**钱包对消息的签名**；频道侧渲染组件校验签名/哈希，未验证消息显示为「未验证发言」，与链上权威战报视觉区分。
- **战报主播模式**播报的每条战报都源自链上事件（附 tx hash），主播无法编造战斗结果——最多美化措辞。

### 6.6 随机数
按用途可插拔配置（§2.3），默认游戏级区块熵；对抗「重掷刷词条」依靠经济手段（重建消耗道具、每日创建/入场上限、动作费、频控），不依赖密码学强度。

## 8. 关键结论速览
1. **链选型：Conflux eSpace（纯 EVM 兼容）**，不用 Core Space。
2. **代付 gas 分层解**：L1a Bot 免费配额（获客支出封顶）、L1b Bot 充值计费（CFX/美元，gas 由用户付——商业主回收通道）、L2 自托管 CLI 自付、L3 钱包直发——付费墙在 Bot 通道层，合约保持无许可。
3. **技能引擎「数据多、原语少」**：`Skill`/`Effect[4]`/`MonsterAI` 全数据化，目标选择全随机（RNG 驱动），最坏回合结算 gas 有硬上限。
4. **技能计划是链上状态**（`uint16[16]` 环形队列），不是聊天口述；只能给自己排。
5. **经济三闸门（开放链上版）**：游戏币不可转移主账本（唯一强强制层）、可转移资产价值天花板（道具强度上限 + 重掷套利锚）、gas 成本对动作的经济压制（Sybil 硬防线）——不依赖限额、隐藏或转移税这些做不到的事。
6. **失败惩罚经济化且不可滥用**：阶梯救援费、负余额无上限但限制行为且收益优先偿债、欠债仍可免费游玩与打工（无死局）；工作室威慑靠 gas 经济而非救援费。
7. **治理防突袭**：资产不可升级、逻辑升级走多签+48h 时间锁、配置 8h 时间锁。
8. **需外部服务**：回合驱动 Keeper 与价格预言机都依赖链下触发，无法纯链上自驱；emergencyAdvance 提供任何人可用的解卡兜底。
