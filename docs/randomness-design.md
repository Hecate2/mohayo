# 随机数设计（Randomness Design）

> **Move 实现现状（2026-09-30，见 `technical-design.md` §2.6.14）**：本文档主体是 EVM/Solidity 时代的
> 设计（`block.prevrandao`、`keccak256` 链、`RNGRouter`）。当前 `aptos/sources` 的实现按 Aptos 的
> 等价物落地：熵源换成 **`aptos_framework::randomness`（AIP-41）**，消费随机数的入口一律是**私有
> `#[randomness] entry fun`**（建号、开战、推进回合、兜底推进、进入下一场、命运骰子/重生卷轴），
> 每笔交易取一次协议随机数作为该回合的种子，房内同回合的多次抽数继续走内部 xorshift 链。
> 「区块熵注入」这一条由协议随机数承担；`prevrandao`/`keccak256`/`RNGRouter` 的表述按 Aptos 口径读。

本文档独立描述本游戏的链上随机数架构：为什么采用「房间级链式伪随机数生成器（PRNG，Pseudo-Random Number Generator）+ 区块熵（PREVRANDAO）」作为战斗内默认随机源，以及它与「可验证随机函数（VRF，Verifiable Random Function）」在抽卡等高价值场景上的分工。代码实现落点在 `CombatTypes.nextRandom` 与 `CombatEngine.createRoom`，与 `technical-design.md` §2.3 相互印证。

## 1. 总览：两层随机架构

本游戏把链上随机数按「单次价值的量级 × 调用频率」切成两层，各自采用不同的熵源与信任模型。

第一层是**房间内战斗细节**：命中判定、随机目标抽取（含权重模式）、多段连击的逐段目标、奖励浮动、死亡召唤概率、效果触发概率。这类随机单次决定的价值极低（一次普攻是否命中、一只史莱姆掉 5 还是 10 Char），但调用频率极高（一个回合内可能抽数十次）。对这一层采用**房间级链式 PRNG**：以房间内持久化的种子为底，混入区块熵 `block.prevrandao`，每次抽数推进一次种子，形成一条不可预测但完全确定性的随机数链。单次抽数成本约一次 `keccak256` 哈希加一次存储写，量级在几十 gas，远低于任何异步随机方案。

第二层是**高价值低频操作**：抽卡、角色创建时的种族与词条掷骰、稀有掉落等。这类随机单次决定的价值可能很高（一张极品角色卡在二级市场的价格锚），操纵或重掷的动机强，因此最终应走 VRF 这类可验证、不可被验证人偏置的熵源。当前阶段以 `RNGRouter`（随机数路由器）统一抽象这一层，默认挂 `BlockEntropyRNG` 过渡，未来可平滑切换到 VRF 提供方而无需改动核心合约（`technical-design.md` §2.3.2）。

## 2. 房间级链式 PRNG：公式与语义

战斗内每一次抽数都执行同一段逻辑：

```solidity
bytes32 newSeed = keccak256(
    abi.encodePacked(
        room.seed,   // 房间持久化种子（链式递进）
        roomId,      // 房间号：跨房间隔离
        room.turnId, // 回合号：跨回合隔离
        block.prevrandao // 区块熵：提供新鲜不可预测性
    )
);
room.seed = newSeed; // 写回，让下一次抽数基于这一次的结果
uint256 rand = uint256(newSeed); // 取 newSeed 作为本次随机数
```

这段逻辑在代码里收敛为 `CombatTypes.nextRandom(CombatTypes.Room storage r)` 一个函数，返回 `uint256(keccak256(abi.encodePacked(r.seed, r.id, r.turnId, block.prevrandao)))` 并同步写回 `r.seed`。它的语义可以拆成四条：

其一，**链式递进**。每次抽数都基于上一次的结果重新哈希，因此同一回合内连续多次抽数（例如多段连击逐段抽目标、命中掷骰后紧接着抽效果概率）得到的是互不相同的值，不存在「同一随机数被复用」的偏差。链式结构还意味着抽数顺序本身参与随机性——先抽目标再抽命中与先抽命中再抽目标得到的是不同的序列，这让结算器内部对抽数顺序的调整天然安全。

其二，**区块熵注入**。`block.prevrandao` 是 EVM 在 PoS（权益证明，Proof of Stake）共识下提供的区块级随机值，每个区块不同且无法被交易发送方预知。玩家在签名交易时并不知道自己的交易会被打包进哪个区块，也就无法预判该区块的 `prevrandao` 值，因此无法针对结果做选择。它是这套方案里「新鲜不可预测性」的唯一来源。

其三，**跨维度隔离**。`roomId` 与 `turnId` 参与混合，保证不同房间、不同回合的随机序列互不相关——即使两个房间的种子恰好相同，只要房间号不同，随机序列就完全不同；同一房间内跨回合也不会因为种子链延续而产生可预测的模式。

其四，**种子初始化**。房间创建时（`CombatEngine.createRoom`）用 `keccak256(abi.encodePacked(block.prevrandao, block.timestamp, msg.sender, roomId))` 初始化 `room.seed`。创建者地址与时间戳保证不同房间的初始种子不同，而首次抽数还会再混入当时的 `prevrandao`，进一步打散。

## 3. 为什么对战斗够用：威胁模型

这套方案不是密码学意义上的安全随机数，但它对本游戏的战斗场景足够。需要先明确一个前提：战斗随机决定的是**低单位价值、高频**的玩法变量，操纵一次随机数的期望收益很低。在此基础上逐一审视潜在操纵者。

**验证人**。验证人理论上可以对区块哈希施加偏置，但 Conflux 采用树图结构 PoS 共识，单个验证人要在树图分叉中押对参考块才能对特定区块的 `prevrandao` 施加影响，其成本远高于收益——收益不过是游戏里一次暴击或一只史莱姆的掉落浮动。这与 `technical-design.md` §2.3.5 对验证人的分析一致。

**自付钱包玩家**。玩家自己发交易时确实可以挑选发送时机，但结算熵混合的是**包含该交易的区块**的 `prevrandao`——玩家在签名时并不知道这个值，无法预判结果。理论上可以反复重发交易去「刷」结果，但这会被频控与动作费压制，且战斗结算本身是单笔交易的原子操作（`technical-design.md` §2.4），玩家无法在结算中途插入重掷。

**中继器 Bot**。Bot 理论上可以「重掷」——观察到不利的区块就暂扣交易、等下一个块再发。但 Bot 本来就是托管方案的信任锚（`technical-design.md` §1.4 方案 C/D），它若要作恶能做的事情远多于操纵随机数；且扣发会在群聊里表现为可观测的回合延迟，可被玩家察觉。若未来需要进一步压缩该能力，可切换到 `CommitRevealRNG` 档位（先提交哈希、下回合揭示），但当前阶段不值得为此付出每回合多一次存储写的代价。

**重掷的真正风险在创建层而非战斗层**。战斗内随机无法被「刷」，但角色创建时的种族/词条掷骰可以被反复重建角色来重掷。这是经济学问题而非密码学问题——VRF 同样无法阻止重掷，唯一有效的手段是让每次掷骰都有成本（重建消耗道具、每日创建/入场上限、动作费），这些已由经济与风控设计覆盖（`technical-design.md` §6 与 `gameplay-design.md` §7）。因此创建层随机走 `RNGRouter` 而非房间 PRNG，正是为了保留「未来切 VRF」的升级路径，而不是因为当前 `BlockEntropyRNG` 不够用。

## 4. 确定性：可复现与可审计

房间级链式 PRNG 是**完全确定性**的：给定 `(room.seed, roomId, turnId, prevrandao)` 的初始值与后续序列，战斗结果唯一。这带来三个工程上的直接收益。

其一，**单笔交易原子性**。回合结算始终是一笔 `advanceTurn` 交易内的原子操作，随机数在交易内同步生成、同步消费，不需要跨交易等待回调。这保住了 `technical-design.md` §2.4 强调的回合结算原子性——异步 VRF 会把一个回合拆成「请求随机数 → 回调 → 结算」三步，Keeper、Bot 与超时判定逻辑随之全部复杂化，这正是「默认不用 VRF」最重要的技术理由。

其二，**测试可复现**。Foundry 测试中 `block.prevrandao` 在单次测试内稳定，因此给定相同的房间创建参数与操作序列，测试结果可精确复现。测试不再需要注入确定性随机源来模拟战斗随机——房间 PRNG 本身就是确定性的，测试只需固定 `prevrandao` 即可。

其三，**链上可审计**。`room.seed` 是链上状态，任何历史回合的随机数都可以由当时的种子与 `prevrandao` 重放验证。这与菜价源「历史可由储备快照重放」的思路同构——随机性不依赖任何链下承诺，全部落在链上可查。

## 5. 与 RNGRouter 的分工

`RNGRouter` 仍然存在，但职责收窄为**创建层与高价值层**的随机路由，不再承担战斗内随机。具体分工如下。

战斗内一切随机（命中、目标、奖励、死亡召唤、效果概率）直接调用 `CombatTypes.nextRandom`，不经过 `RNGRouter`——省去一次外部调用与路由开销，且天然与房间状态绑定。`RNGRouter` 目前服务两个用途：`AFFIX`（角色创建时的种族三层加权抽取与词条方向/词条/档位三次掷骰）与 `DROP`（预留的关卡掉落），默认挂 `BlockEntropyRNG`。未来抽卡等高价值场景接入 VRF 时，只需在 `RNGRouter` 里把对应用途的 Provider 换成 VRF 提供方，核心合约零改动。

需要强调的是，`BlockEntropyRNG` 与房间 PRNG 的熵源都是 `keccak256` 混合 `prevrandao`，但两者语义不同：`BlockEntropyRNG` 是无状态的纯视图函数（零存储写，单次约 30 gas），适合创建层这种「一次性、低频」的调用；房间 PRNG 是有状态的链式结构（每次抽数写回种子，多一次存储写），适合战斗内这种「高频、需要序列内互不相关」的调用。两者并存而非互斥。

## 6. 实现落点

代码层面的落点如下，全部是通用小改动，不引入任何脏代码分支。

`CombatTypes.nextRandom` 是唯一的抽数入口，定义在 `src/libs/CombatTypes.sol`，被 `CombatLib`（命中掷骰、效果概率、奖励浮动、死亡召唤）与 `CombatTargetLib`（加权目标抽取）通过 `using CombatTypes for CombatTypes.Room` 调用。`CombatEngine.createRoom` 负责种子初始化。`Room` 结构体新增 `bytes32 seed` 字段，与既有字段共享存储布局，不改变任何既有字段的存储槽位。

## 7. 成本

单次抽数的成本由三部分组成：一次 `keccak256`（约 30 gas）、一次存储读（读 `room.seed`，约 100 gas warm）、一次存储写（写回 `room.seed`，约 100 gas warm 或 2100 gas cold）。整体量级在几百 gas 以内，远低于任何跨合约调用或异步方案。一个回合内即使抽数十次随机数，总成本也远低于一次普通状态更新的量级，对玩家 gas 负担可忽略。

## 8. 边界与注意

第一，**同区块多房间**。不同房间的种子链完全独立，`roomId` 参与混合保证互不干扰，不存在跨房间的随机性串扰。

第二，**同回合多抽数**。链式递进保证序列内互不相同，但这也意味着**抽数顺序是结果的一部分**——结算器内部调整抽数顺序会改变结果。这是设计内行为（确定性而非可预测性），测试与审计都以「给定操作序列」为前提。

第三，**`prevrandao` 在 eSpace 的语义**。Conflux eSpace 通过 CIP-645（Conflux 改进提案 645，Conflux Improvement Proposal 645）对齐以太坊 EVM 行为，`PREVRANDAO` 按以太坊语义可用（`technical-design.md` §2.3.4）。上线前需在测试网实测 eSpace 上 `prevrandao` 的具体回填值，若语义存疑可退化为 `blockhash(block.number - 1)` 混合熵，代价仅为熵来源少一项——种子链的确定性不受影响。

第四，**高价值场景不适用**。本方案明确不用于抽卡、角色创建掷骰等单次价值高的场景——这些场景的操纵动机强，且「被重掷」风险是经济学问题，需要 VRF 或成本闸门而非更便宜的熵源。这是两层架构存在的根本原因。
